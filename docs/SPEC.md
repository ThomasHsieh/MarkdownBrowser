# MarkdownBrowser 規格

原生 macOS Markdown 閱讀器。目標是把 Claude Code 在 cmux／ghostty 裡的中文閱讀體驗，
搬到一個能雙點擊開啟、能列印、能自訂樣式的 App 裡。

版本：v1
日期：2026-09-11

---

## 1. 為什麼要有這個 App

陪讀電子書的流程會產出大量繁體中文心得 Markdown（`~/books/心得/`，
一本書一個資料夾、一章一個檔，13–27 KB）。這些檔案在終端機裡讀起來很好，
但匯入 Notion 或用 MarkEdit Preview 看都失真，關鍵失真點是**粗體**：

終端機的做法是 `ghostty/config` 裡這一組設定 ——

```
font-family = "SF Mono"
font-family = "LXGW WenKai Mono TC"
font-family-bold = "SF Mono"
font-family-bold = "LXGW WenKai Mono TC Light"
font-synthetic-style = no-bold
bold-color = #DD9853
```

也就是：**中文粗體不加粗，只換成橘色**。中文字加粗會糊成一團，
所以重點訊號完全交給顏色。一般 Markdown viewer 把 `**粗體**` 渲染成
`font-weight: bold`，中文就糊了，而且沒有顏色差，整頁看起來一片平。

v1 要重現的就是這件事，排版再比終端機好讀一些（第 4 節）。

## 2. 不做什麼

- 不做編輯。這是唯讀的閱讀器，要改內容用 `Cmd+E` 丟給 MarkEdit。
  標記與註記（第 12 節）不算編輯：它們寫進同資料夾的 sidecar 檔，**永遠不碰 `.md` 本身**。
- 不做書庫管理。沒有資料庫、沒有索引、沒有標籤。
  EPUB 對照閱讀（第 13 節）不算書庫管理：書與心得的配對是開檔當下用書名比對算出來的，
  只有比對不到時手動指定的那幾筆存在 UserDefaults，沒有書目清單、不掃描整個書庫。
- 不做 Mermaid、不做 KaTeX。各自要背一個幾百 KB 的 JS 引擎，而現有心得檔一個都沒用到。

## 3. 架構

```
SwiftUI（視窗、選單、Finder 關聯、檔案監聽、側欄）
        │  postMessage / evaluateJavaScript
        ▼
WKWebView（內容區，一個視窗一份）
        │
        ├── markdown-it 14.x（內嵌，vendored，不走網路）
        ├── base.css（唯一的一套樣式）
        └── 內嵌 LXGW WenKai TC / Sarasa Gothic TC 與各自的等寬版
```

Swift 端只做「殼」——開檔、監聽、選單、側欄資料。所有排版都在 CSS 裡，
切字體、切明暗只是換 `<html>` 上的 `data-font`／`data-appearance` 屬性。

Swift 端的狀態分三份（多視窗的緣故，見第 11 節）：

| | 範圍 | 內容 |
|---|---|---|
| `DocumentState` | 一個視窗一份 | 讀哪個檔、側欄、字體、字級、外觀 |
| `AppSettings` | 全 App | 新視窗的起始設定、最近開啟 |
| `WindowRouter` | 全 App | 哪些視窗開著、哪一個在前景、下一個檔案開到哪裡 |

- 專案：`~/workspace/MarkdownBrowser`
- Bundle ID：`com.thomashsieh.markdownbrowser`
- 最低系統：macOS 14
- 建置：`Package.swift` ＋ `Makefile`，不用 `.xcodeproj`（pbxproj 難以手改與 review）

## 4. 樣式

### 4.1 共通不變量

**粗體永不加粗。** `strong` 一律 `font-weight: normal`，改上 accent 色。
`-webkit-font-smoothing` 與 `font-synthetic-weight: none` 都要明確關掉合成粗體，
否則 WebKit 會替沒有 Bold 字面的字型合成假粗。

從截圖取樣得到的實際顏色：

| 用途 | 值 | 來源 |
|---|---|---|
| 背景 | `#1C1C1C` | 截圖取樣 |
| 內文 | `#CECECE` | 截圖取樣 |
| 重點（粗體）、標題 | `#DD9853` | `ghostty/config` 的 `bold-color` 宣告值 |
| 引言左側直線 | `#757575` | 截圖取樣 |
| 框線 | `#CECECE` | 終端機的 box-drawing 就是內文色 |

### 4.2 只有一套樣式

原本有「閱讀」與「終端機」兩個主題可選。用了一陣子後，拿真實的心得與書逐項比較
（臨時做了一個「樣式比較」選單，每項各自切換），留下每一項比較好的那邊，合併成唯一
一套，寫在 `base.css`。主題選單、`⌘1`／`⌘2`、自訂主題（`~/.config/markdownbrowser/`）
一起拿掉。

| 項目 | 取哪邊 | 現在的樣子 |
|---|---|---|
| 字體 | 閱讀 | 比例字（楷體 `LXGW WenKai TC`／黑體 `Sarasa Gothic TC`），自帶拉丁字 |
| 行高 | 閱讀 | 1.9 |
| 標題顏色 | 終端機 | 跟粗體同一個橘，跟在終端機裡讀到的一樣 |
| 標題裝飾 | 終端機 | 沒有底線、色條，靠字級（1.75／1.4／1.18／1.05em）與上下留白分層 |
| 框線顏色 | 終端機 | 內文色，表格與分隔線清楚 |
| 行內程式碼 | 閱讀 | `SF Mono` 加深色底塊 |
| 表格 | 閱讀 | 滿版、表頭淡底、隔行淡色條紋 |
| 數字 | 閱讀 | 全文 `tabular-nums`，金額上下對齊 |

程式碼區塊（行內與 `pre`）英數用 `SF Mono`、中文用等寬中文字（`--cjk-mono`），
中文註解也對得齊。表格框線用 CSS `1px` 細線而不是 box-drawing 字元：真對齊要自己算
雙寬字元寬度、自己折行、自己補空白，畫面差別只在框線粗細。

### 4.4 外觀：深色／淺色

跟字體互相獨立的軸。選單在「顯示方式 → 外觀」，比照 Safari：
**自動**（跟隨系統）／**淺色**／**深色**。

**淺色不是把深色反過來。** `#DD9853` 是為深色底調的橘，放到暖白紙上對比只有
**2.28:1**，遠低於內文需要的 4.5:1。所以淺色維持同一個色相、往下壓到通過
WCAG AA 為止：

| 用途 | 深色 | 淺色 | 淺色對比 |
|---|---|---|---|
| 背景 | `#1C1C1C` | `#FAF8F3`（暖白紙，純白對楷體長文偏刺眼） | — |
| 內文、框線 | `#CECECE` | `#3A3A3A` | 10.7:1 |
| 重點（粗體）、標題 | `#DD9853` | `#A2541A` | 5.2:1 |

實作上兩組只差變數：`base.css` 的 `:root` 是深色，`:root[data-appearance="light"]`
覆寫淺色那幾個。

兩個踩過的坑：

- 強制淺色／深色時要設 `NSWindow.appearance`，否則只有網頁內容變色，
  視窗外框（側欄、工具列、標題列）還是系統的。設在 `NSApp` 也有效，
  但那是全 App 的，一個視窗切淺色會把所有視窗一起拖下去 —— 外觀是
  每個視窗各自的（第 11 節），所以要設在視窗上。
- 跟隨系統時**不要用 KVO 盯 `NSApp.effectiveAppearance`** —— 它不保證 KVO
  相容，實測系統切換時不會觸發，結果是側欄自己變淺了、網頁內容還留在深色。
  要聽系統廣播的 `AppleInterfaceThemeChangedNotification`。

### 4.5 字體

中文字體是另一個獨立的軸，`data-font` 只決定用哪套中文字：

| | 楷體 `kai`（預設） | 黑體 `gothic` |
|---|---|---|
| 內文（比例） | LXGW WenKai TC | Sarasa Gothic TC |
| 程式碼（等寬） | LXGW WenKai Mono TC | Sarasa Mono TC |

`base.css` 把這兩組寫成 `--cjk` / `--cjk-mono`。

**黑體的粗體也不加粗。** `switch-font.sh` 的 gothic profile 在終端機裡是把粗體
升到 SemiBold 的，這裡刻意不跟 —— 兩套字體的行為要一致，粗體永遠只換色，
否則「粗體長什麼樣」會隨字體而變。實作上是 `@font-face` 只帶 Regular、
字重範圍開成 `100 900`，任何字重請求都落回同一個字面。

### 4.6 行寬

**隨視窗滿版**，只留固定左右內距（`3rem`），不設 `max-width`。
`Cmd +` / `Cmd -` 調字級，`Cmd 0` 重設。

### 5.1 工具列

由左到右：側欄開關、對照書籍、**外觀**（自動／淺色／深色）、字體、字級加減、搜尋、
用 MarkEdit 開啟、列印。每個都給 `Label`（圖示＋標題），
使用者右鍵可以自己切換要不要顯示文字。`⌘1`／`⌘2` 原本是切主題，主題拿掉後空著。

### 5.2 最近開啟

自己維護，不靠 `NSDocumentController` —— 這不是文件型 App，
系統那份清單管不到筆數上限，也不會把已刪掉的檔剔除。
存 10 筆路徑在 UserDefaults，載入時過濾掉已不存在的檔。

### 5.3 側欄

兩段式，上下同時顯示：

- **上半：同資料夾的 `.md`**。排序解析檔名裡的「第X章」，
  中文數字（一二三四五六七八九十）與阿拉伯數字都認；
  抽不出章號的（`附錄與後記`）排到最後，彼此之間按檔名。
  這是必要的 —— 字典序下 `第一章 / 第三章 / 第二章` 就是這個順序，
  兩個現有資料夾都亂掉。
- **下半：本文大綱**。`h1`–`h4`，點擊捲到該標題，捲動時高亮目前位置。

### 5.4 自動重載

用 `DispatchSource.makeFileSystemObjectSource` 監聽 `.write`／`.rename`／`.delete`，
去抖 150 ms。編輯器多半是「寫暫存檔再 rename」，所以 `rename`／`delete` 之後
要重新開 fd 重新掛監聽，否則只會收到一次事件。

重載後捲軸回原位：記下重載前**視窗頂端往下第一個標題的 id 與其偏移量**，
重載後找同 id 的標題捲回去。比純像素位置穩 —— AI 在你上方插入一段，
像素位置就整個位移了。

## 6. Markdown 語法

markdown-it 預設 CommonMark ＋ 打開 GFM 需要的：`tables`、`strikethrough`、
`linkify`。`html: false`（心得檔沒有原生 HTML，關掉比較安全）。

圖片支援本機相對路徑。網頁不是用 `file://` 載入的，而是自訂 scheme `mbres://` ——
`loadFileURL(_:allowingReadAccessTo:)` 只能開放一個目錄樹，但同時要讀幾個
不相干的地方：App 自己的網頁資源、目前文件所在資料夾（相對路徑圖片）、
EPUB 裡面的檔案（第 13 節）。

    mbres://app/…       → Contents/Resources/web/…
    mbres://doc/…       → 目前文件所在資料夾

渲染後由 JS 把相對路徑的 `img[src]` 改寫成 `mbres://doc/…`，否則它會相對於
頁面位址解析到 App 自己的資源目錄去。handler 會擋掉用 `../` 逃出根目錄的請求。

外部連結（`http`/`https`）用 `NSWorkspace` 丟給預設瀏覽器，不在 App 內導航。

## 7. 字型

內嵌進 `.app`，每套只需要 Regular 字面（粗體靠顏色，不靠字重）：

| 檔案 | 大小 | 用途 |
|---|---|---|
| `LXGWWenKaiTC-Regular.ttf` | 13 MB | 楷體・比例 |
| `LXGWWenKaiMonoTC-Regular.ttf` | 13 MB | 楷體・等寬 |
| `SarasaGothicTC-Regular.ttf` | 24 MB | 黑體・比例 |
| `SarasaMonoTC-Regular.ttf` | 26 MB | 黑體・等寬 |

成品 `.app` 約 73 MB，絕大部分是字型。

**不進版控。** `make` 時依序找 `~/books/fonts/` →
`~/Library/Fonts/` → 官方 GitHub release 下載到 `.cache/fonts/`。

兩個踩過的坑：

- 比例版 `LXGWWenKaiTC-*` 沒裝在系統，只在 `books/fonts/` 裡；等寬版兩處都有。
- Sarasa 官方**只提供 7z**，而且要整個家族一包（約 60 MB）才拿得到那一個字面，
  所以下載那條路需要 `7z`（`brew install p7zip`）。系統裡那份 Sarasa 是
  832 MB 的 `.ttc` 集合檔，拆不出單一 TTF，幫不上忙。

## 8. Finder 關聯

`Info.plist` 的 `CFBundleDocumentTypes` 宣告 `net.daringfireball.markdown`、
`public.markdown` 與副檔名 `md`/`markdown`/`mdown`/`mkd`，
`LSHandlerRank` 設 `Owner`，角色 `Viewer`。

`.mdown`／`.mkd`／`.mdwn` 另外宣告一個本 App 擁有的類型
`com.thomashsieh.markdownbrowser.markdown-variant`（`UTExportedTypeDeclarations`，
掛在 `net.daringfireball.markdown` 底下）。只在匯入的 `net.daringfireball.markdown`
裡多列這三個副檔名沒有用：匯入宣告的優先序最低，那個 UTI 已經有更權威的宣告，
多列的副檔名被忽略，三者變成動態類型，實測被 Notion、VS Code 搶走。

`public.markdown` 雖然列在 `LSItemContentTypes` 裡，但 `make set-default` 不設它：
它在系統上是個沒有上層類型的空殼，沒有任何副檔名對應到它，`NSWorkspace` 與
LaunchServices 都拒絕替它設預設程式，設了也不影響任何檔案。

`Info.plist` 裡宣告 `Owner` 只代表「我有能力開」，不等於預設程式 ——
真正的預設是使用者層級的設定。`make set-default` 會呼叫
`NSWorkspace.setDefaultApplication(at:toOpen:)` 明確指定，
等同 Finder 的「取得資訊 → 打開方式 → 全部更改」，`make status` 可以查目前是誰。

一個會踩到的坑：預設程式是**用 bundle ID 存的**，不是路徑。
所以同一個 bundle ID 有兩份副本被 LaunchServices 註冊時（建置產物與安裝的那份），
解析結果不一定是你要的那份。因此 `.app` 一律組在 `.build/` 底下，
`~/Applications` 的那份才是唯一會被開到的；`set-default-app.swift` 也
優先挑 `~/Applications` 而不是用 bundle ID 反查。

開檔走 `NSApplicationDelegate.application(_:open:)`，一次開多個檔就開多個視窗，
政策見第 11 節。

`.epub`（`org.idpf.epub-container`）另外宣告，但 `LSHandlerRank` 是 `Alternate`：
只出現在「打開方式」裡，**不搶預設程式**，`make set-default` 也不碰它（第 13 節）。

## 9. 建置與安裝

```bash
make          # 取字型 → swift build -c release → 組 .app → codesign --sign -
make install  # 複製到 ~/Applications 並 lsregister
make run          # 建置後直接開
make set-default  # 把 .md 的預設開啟程式設成這個 App
make status       # 查 .md 目前的預設開啟程式是誰
make clean
```

`.app` 由 Makefile 手工組出來：

```
.build/MarkdownBrowser.app/Contents/
  Info.plist
  MacOS/MarkdownBrowser
  Resources/web/{index.html,app.js,book.js,highlights.js,base.css,print.css,vendor/}
  Resources/web/fonts/*.ttf
  Resources/{zh-Hant,en}.lproj/      宣告語言，標準選單才會跟系統變中文
```

ad-hoc 簽章（`codesign --sign -`），第一次開可能要去
「系統設定 → 隱私權與安全性」放行。

## 11. 視窗模型

多視窗。一個視窗讀一個檔，關掉最後一個視窗就結束 App。

### 11.1 狀態怎麼切

單視窗版本只有一個 `AppState.shared`，所以 Finder 再開一個檔就把正在讀的那一份
蓋掉。拆法是按「範圍」切，不是按功能切（見第 3 節的表）：

- 一個視窗一份的東西放 `DocumentState` —— 讀哪個檔、側欄、字體、字級、外觀
- 跨視窗共用的放 `AppSettings` —— 新視窗的起始設定、最近開啟
- 「誰開著、誰在前景」放 `WindowRouter`

**字體與外觀是每個視窗各自的。** 一個視窗楷體、一個黑體並排比對是實際用法，
而「記住上次選的」仍然成立 —— 任何視窗改了設定就寫回 `AppSettings`，
當下一個新視窗的起始值。

**前景視窗用 `NSWindow` 的 key 通知自己記一份，不用 SwiftUI 的 focus。**
選單要作用在前景視窗上，`⌘F` 的按鍵監聽也要找到前景視窗的 bridge，
而 AppDelegate 與 `NSEvent` 監聽都在 SwiftUI 的 focus 環境之外拿不到。
`WindowRouter.active` 是唯一的來源。它同時把前景視窗自己的變化轉發出去
（`objectWillChange`），否則開了檔之後選單的啟用狀態不會重算。

### 11.2 開檔的兩套政策

| 入口 | 政策 |
|---|---|
| Finder 雙點擊、`open` 指令、拖到 Dock | **不動已經開著檔的視窗** |
| `Cmd O`、最近開啟、側欄點擊 | 換掉前景視窗的內容；但那個檔**已經開在別的視窗**就改成把那個視窗帶到前景 |

Finder 那條依序試：已經有視窗在讀這個檔就帶到前景 → 還沒開檔的空白視窗載入它
→ 都沒有才開新視窗。第一條讓重複雙點擊不會開出兩個一樣的視窗，第二條讓
`Cmd N` 之後雙點擊不會多留一個空白視窗。

選單那條維持單視窗時的語意 —— 那是使用者當下指定的動作，要另開一個就先 `Cmd N`。

**一檔一窗。** 兩條政策都保證同一個檔只會開在一個視窗裡。原因是標記：每個視窗的
網頁端各自是標記資料的唯一真相（第 12.8 節），同一個檔開兩份就會兩邊各寫各的、
互相覆蓋。對閱讀器來說「同一章開兩個視窗對照」的需求很低，真要對照通常是兩個
不同章節。代價是 `Cmd O` 選了一個已經開在別處的檔，結果是跳到那個視窗、
目前的視窗不變。

Dock 圖示右鍵的選單要自己給（`applicationDockMenu`）—— 那個選單不會自動抄
App 的選單列，SwiftUI 的 `Commands` 只長在選單列上。目前只放「開新視窗」。

### 11.3 SwiftUI 的三個坑

都是實測踩到的，改動視窗相關的程式前先讀這一段。

**`WindowGroup` 不要帶值。** `WindowGroup(for: T.self)` 看起來剛好可以用「這個
視窗在讀哪個檔」當視窗的身分，但 SwiftUI 會把那個值存起來做視窗還原，而視窗內
換檔時要把新值寫回 binding，寫回去又會被當成「請開一個新視窗」—— 於是視窗數
每次啟動都往上加（實測乾淨啟動被還原成三個視窗，而且那份狀態清 UserDefaults
也清不掉）。現在 `WindowGroup` 不帶值，「新視窗要讀哪個檔」由
`WindowRouter.handoffs` 這個佇列交棒，新視窗的 `onAppear` 自己來取。

**開檔會冒出空殼視窗。** App 每次收到開檔請求，SwiftUI 都會生一個視窗又馬上
丟掉（帶著檔案啟動、以及執行中被 Finder 要求開檔都會）。被丟掉的那個只是內容
被拆走，視窗本體還留在畫面上，就疊在真正的視窗底下 —— `isVisible` 與
`orderedWindows` 都認為它在。把開檔處理全部停掉也一樣發生，所以這是 SwiftUI
自己的行為。`WindowRouter.closeOrphanWindows` 負責收掉：只關「本來有
`DocumentState`、現在沒有」的視窗，不掃全部視窗 —— 開檔對話框與關於視窗也
都沒有 `DocumentState`，掃全部會把它們一起關掉。

**而且那個空殼會半路把檔案接走。** 它在消失之前是個合法的「還沒開檔的空白
視窗」，所以可能被挑去載入檔案，也可能先取走交棒佇列裡的檔 —— 兩種都會讓
檔案跟著它一起消失，畫面上什麼都沒發生。實測空殼消失與開檔請求只差 2 ms，
而視窗大、內容多的時候順序就會反過來（真的開不出來）。順序賭不起，所以
`openFromFinder` 之後 0.4 秒回頭確認：沒有任何活著的視窗在讀那個檔就重開一次，
最多三次。

**一個視窗都還沒有的時候不要搶著開窗。** 帶著檔案啟動時，AppKit 會叫 SwiftUI
收掉它預設開的那個視窗（啟動是為了開文件，不是為了開空白視窗），而 Finder 的
開檔請求剛好落在那個空檔裡。這時自己開窗，就會跟 SwiftUI 接著補上的那個視窗
撞成兩個。所以沒有視窗時先把檔案存起來，等下一個視窗出現再接手。

還有一個時機問題：視窗掛上 SwiftUI 的過程中會呼叫 `WindowRouter.register`，
在那裡直接開檔會撞進 SwiftUI 的更新週期，所以待開的檔要晚一個 runloop 才處理。

## 12. 標記

在閱讀時畫重點、附註記。主要用途是**重讀時的視覺記號**；延伸用途是讓標記跟著
檔案走 —— 存成同資料夾的 sidecar 檔，跟著 `.md` 一起進 git。

**不做**：跨檔或跨書的標記總覽（那是書庫管理，第 2 節）、匯出、依顏色篩選、
搜尋標記、`Cmd Z` 復原、Markdown 格式的註記、模糊比對、列印標記。

設計過程用了兩個原型，實作完成、實機測過之後已經刪除（沒有保留分支）。它們驗證的結論都寫進了下面各節：

- `highlight-colors`：四種底色與底線在深色／淺色模式下疊上橘色粗體的實際對比，以及跟搜尋命中會不會撞色 —— 定案 12.1 節的配色與淺色模式的粗體壓深
- `highlight-interaction`：選取後浮出工具列、擦除選到的部分、純文字註記的自動儲存、tooltip 的延遲與位置、側欄「大綱｜標記」的分組與右鍵選單 —— 定案 12.2、12.3、12.6 節的操作方式

### 12.1 樣式

四種底色加一種底線：**綠、藍、紫、粉**、底線。預設是綠。

- **不用橘、不用黃。** 橘色是粗體字色，也是搜尋命中的底色；黃色離橘只差約 15°
  色相，疊在深色底上會變成橄欖褐，跟搜尋命中分不出來。
- **標記不改字重、不改字色。** 粗體＝橘色不加粗是這個 App 的核心訊號（第 1 節），
  標記只能動底色或底線，否則會跟粗體搶訊號。
- **淺色模式下標記內的粗體壓深一級**（`--hl-accent: #94481A`）。底色要淡到
  `#A2541A` 仍有 4.5:1，就只比紙色深一點點，畫了跟沒畫一樣；底色加深、
  粗體同步壓深，兩邊都看得清楚。仍然是橘色、仍然不加粗，不違反不變量。
- **深淺兩組都用半透明 `rgba`**，疊在哪種底色上都自然融入。

| 變數 | 深色（疊在 `#1C1C1C`） | 淺色（疊在 `#FAF8F3`） | 粗體對比 深／淺 |
|---|---|---|---|
| `--hl-green` | `rgba(95, 184, 120, 0.24)` | `rgba(95, 184, 120, 0.30)` | 4.55 / 4.89 |
| `--hl-blue` | `rgba(95, 143, 208, 0.26)` | `rgba(95, 143, 208, 0.26)` | 4.78 / 4.77 |
| `--hl-purple` | `rgba(160, 124, 224, 0.28)` | `rgba(160, 124, 224, 0.26)` | 4.58 / 4.79 |
| `--hl-pink` | `rgba(224, 102, 143, 0.24)` | `rgba(224, 102, 143, 0.24)` | 4.97 / 4.81 |
| `--hl-underline` | `var(--fg)` | `var(--fg)` | — |
| `--hl-accent` | `var(--accent)` | `#94481A` | — |

變數依第 4 節的慣例：`base.css` 的 `:root` 放深色那組，`[data-appearance="light"]` 覆寫淺色。

浮動工具列與 tooltip **不新增變數**，用既有的 `--bg`、`--fg`、`--rule`、
`--muted` 加陰影。工具列上的色票是按鈕圖示而不是內文樣式，用固定實色寫在 `base.css`。

### 12.2 建立、改色、擦除

**選取文字、放開滑鼠，選取範圍上方浮出工具列**（上方沒空間就放下方）：

```
● ● ● ● 底 │ 註記  拷貝  刪除
```

- 點顏色或「底」就建立標記。`Shift Cmd H` 直接套綠色。
- **刪除鍵永遠在**：選取範圍沒碰到任何標記時變灰（不隱藏，按鈕位置固定，手會記住）。
- **單擊已有的標記**也會浮出同一條工具列（編輯模式），目前的顏色有外框；
  這時的刪除是整條刪掉。**連結優先**：點到標記裡的連結文字是開連結，
  要編輯含連結的標記，點標記的其他地方或用選取範圍。
- 「拷貝」走 Swift 的 `NSPasteboard`，不用 `navigator.clipboard` —— 網頁是從
  自訂的 `mbres://` 載入的，WebKit 不一定當它是安全來源。

**建立時碰到既有標記：整條合併。** 新選取範圍與既有標記的聯集變成一條，用新顏色。

**緊接著的同色標記也合併**：新選取範圍與既有標記中間只隔空白或換行、而且是同一種顏色，
就合成一條（註記依原文順序串接）。這是為了書的翻頁模式（13.12）：一句話被切在頁尾，
翻頁前後分兩次標，結果仍是 sidecar 裡的一筆。顏色不同不合併 —— 刻意把相鄰兩句
標成不同顏色時，要能分開。所有地方都套用（心得、捲動模式的書也一樣），規則才好預期。

**刪除只擦掉選到的部分。** 選了某條標記中間的一段按刪除，就切成前後兩條；
選取範圍碰到幾條就各自擦掉重疊的部分。建立與擦除刻意不對稱：畫線時手不準，
所以碰到就合併；擦除時要精細，所以只擦選到的。

**選取範圍的整理規則**（建立或擦除之前先做）：

- 去掉頭尾的空白與換行 —— 從段落頭拖到段落尾常會多選到換行
- 限縮在內文區（拖進搜尋框的部分不算）
- 只剩空白就不算選取，不浮出工具列

**沒有禁區。** 標題、連結、行內程式碼、程式碼區塊、表格（跨儲存格就每格各畫一段）
都能標；圖片本身不畫，選取範圍跨過圖片時前後的文字照樣標。

### 12.3 註記

純文字、多行、一條標記一則。不渲染 Markdown。

- **新增**：工具列的「註記」，在工具列下方展開輸入框。在建立模式按「註記」會先用
  綠色（碰到既有標記就沿用它的顏色）建立標記，再開輸入框。
- **沒有存檔鍵、沒有取消**：停手 500 ms 就寫入，任何關掉輸入框的動作再寫一次 ——
  點別處、`Esc`、`Cmd Return`、點另一條或同一條標記、改色、再按一次「註記」、
  開始新的選取、視窗失去焦點、自動重載、關視窗。檔案隨時可能被 AI 改寫觸發重載，
  「關掉才存」會在最不該丟的時候丟。輸入框下方顯示「已自動儲存 時:分:秒」。
- **清空就是刪除註記**，標記本身留著。
- **標示**：有註記的標記，最後一段尾端加一顆同色系的上標小圓點。
- **閱讀**：點有註記的標記，工具列下方直接顯示全文，點文字就能編輯。
- **tooltip**：滑鼠停在有註記的標記上 **400 ms** 才出現（掃過去不會跳），放在整條標記
  **第一行的上方**（不蓋到標記本身；上方沒空間就放到最後一行的下方）。寬度上限約 22 字、
  最多 8 行，超過截斷。不可互動，移開就消失；工具列開著時不顯示。同一條標記跨行、
  跨段落的每一塊都算同一條，不重新計時。

**切割、擦光、合併時註記的去向**（原則：註記不會無聲消失）：

| 情況 | 處理 |
|---|---|
| 擦中間、切成兩段 | 註記**跟著前段** |
| 選取範圍會擦光整條有註記的標記 | 刪除鍵改成紅字「**刪除（含註記）**」，不跳對話框 |
| 建立時合併多條有註記的標記 | 註記依原文順序**串接**，中間空一行 |

### 12.4 sidecar 檔

```
書 F_心得_第1章_章名.md
書 F_心得_第1章_章名_highlights.json
```

檔名是 `<原檔名去掉副檔名>_highlights.json`，跟心得檔的底線命名風格一致。
側欄只列 Markdown 副檔名，所以 sidecar 不會跑進章節清單。**沒有標記就不建檔**，
全部刪光就刪檔。

```json
{
  "version": 1,
  "highlights": [
    {
      "id": "k3f9a2c1",
      "style": "purple",
      "exact": "致富的關鍵在於「知道自己要做什麼、和誰共事、什麼時候做」",
      "prefix": "一星期在餐廳工作 80 小時也不會變富有。",
      "suffix": "。努力不能少，但要用在對的地方；還沒弄清",
      "heading": "開場致富是一套學得會的技能",
      "note": "三個問題其實是同一個問題的三面：判斷力。",
      "created": "2026-10-13T14:16:57+08:00"
    }
  ]
}
```

| 欄位 | 說明 |
|---|---|
| `version` | 格式版本。比 App 支援的新就進入唯讀（12.9 節） |
| `id` | 8 碼隨機字串。不用陣列索引 —— 索引隨增刪位移，diff 會很亂 |
| `style` | `green` / `blue` / `purple` / `pink` / `underline`。叫 style 不叫 color，底線不是顏色 |
| `exact` / `prefix` / `suffix` | 引文錨點，**渲染後的文字**（不含 `**`），前後文各 32 字 |
| `heading` | 所在標題的 slug；標題之前的內容是 `null` |
| `note` | 純文字註記；沒有註記就**不寫這個鍵** |
| `created` | 建立時間，含時區，給總覽排序用 |

**刻意不存**：字元偏移量（上方插入一段就全部失效，得一直改寫 sidecar）、
`updated`（沒有功能用得到，又每改一次註記就變）、「找不到位置」的狀態（每次打開
算出來的，不是資料）、原檔名（檔名本身就是對應關係，再存一份改名後會互相矛盾）。

**寫檔原則：只有使用者的動作才會寫檔。** 打開、重新比對、發現某條對不上，都不寫。
否則唯讀閱讀器光是「打開來看」就會在 git 裡留下變動。寫入時：

- 縮排格式化、鍵的順序固定、標記依原文位置排序，`git diff` 只出現真正變動的行
- 原子寫入（寫暫存檔再 rename）
- **搭便車更新前後文**：成功對上的標記，順便把 `prefix` / `suffix` / `heading` 更新成
  現況；找不到位置的標記原封不動保留，依它上次在檔案裡的位置排

**git**：`~/books` 是 private repo，sidecar 照常追蹤，因此有版本歷史與備份。
但**不跟心得檔混在同一個 commit**，規則寫在那個 repo 的 `CLAUDE.md`。
**repo 若改成公開，註記會跟著公開，而且留在 git 歷史裡很難清乾淨。**

**純文字檔一視同仁**，App 打得開的檔都能標。`X.md` 與 `X.txt` 同時存在時會共用
`X_highlights.json`；後果只是各自把對方的標記列成「找不到位置」，不會遺失資料。

### 12.5 錨點與重新比對

錨點是引文比對（W3C Web Annotation 的 TextQuoteSelector 做法），不是位置。
位置型錨點（像 EPUB 的 CFI）能用是因為電子書出版後不會變；心得檔會被 AI 改寫，
上方插入一段，位置型錨點就全部錯位 —— 落在錯的句子上比消失還糟。

**比對規則**（先把空白連續段壓成一個，AI 重排換行不受影響）：

1. 找出 `exact` 所有出現的位置
2. **只出現一次就直接接上**，就算前後文已經被改掉。句子本身還在，就是同一句
3. 出現多次：前文從尾端往前連續相同的字數 ＋ 後文從開頭往後連續相同的字數，
   `heading` 相同再加分；取最高分，同分取第一個
4. 一次都沒出現：列入「找不到位置」

比對的是渲染後的文字，所以 AI 在句子裡加上或拿掉 `**`，標記照樣對得上。

**時機**：就在 `MB.render` 裡、畫面更新前同步做完，標記與新內容同一個畫面出現。
一章幾千到一萬字、幾十條標記，是毫秒以下的工作，不需要 Worker 或增量比對。

**重載當下正在操作的東西**：

| 狀態 | 處理 |
|---|---|
| 正在打註記 | 先寫入；重新比對後那條還在就保持輸入框開著並重新定位，不在就關掉 |
| 工具列在建立模式 | 關掉（選取範圍的位置已經失效） |
| 工具列在編輯模式 | 那條還在就重新定位，不在就關掉 |
| tooltip | 關掉 |

AI 連續改檔的中間版本可能讓某條暫時對不上；因為重載不寫檔，下個版本對上就回來。

### 12.6 側欄的標記總覽

側欄上半「同資料夾」不動，下半用分段控制切換「**大綱 | 標記 n**」，每個視窗各自記住。
只列**目前這個檔**的標記。

```
[ 大綱 | 標記 5 ]
開場：致富是一套學得會…        ← 所在標題（灰色小字），依原文順序分組
● 一星期在餐廳工作 80 小時…    ← 原文最多 2 行
  跟「窮忙」是同一件事…        ← 註記第 1 行，灰色斜體
▁ 把自己商品化                 ← 底線樣式用短橫線
⚠ 找不到位置（1）              ← 永遠排最後
```

- **點一列**：內文捲到那條標記、閃兩下，**不開**工具列（只是導航）
- **右鍵**：拷貝原文、拷貝註記（沒註記就變灰）、刪除（有註記就是紅字「刪除（含註記）」）
- **找不到位置**：點了不捲動，原地展開完整原文與註記，讓你判斷要不要刪
- 「標記」後面的數字含找不到位置的那些

### 12.7 選單

依作用對象分散到現有選單，不新增「標記」選單（比照預覽程式的「標示文字」在工具選單）：

| 選單 | 項目 | 備註 |
|---|---|---|
| 編輯 | 標記選取文字 `Shift Cmd H` | 永遠可按，沒有選取時只發出提示音 |
| 檔案 | 在 Finder 中顯示標記檔 | 還沒有 sidecar 時變灰 |
| 顯示方式 | 側欄：大綱／側欄：標記 | 單選，不加快捷鍵 |

`Shift Cmd H` 跟 `Cmd F` 一樣走 `NSEvent` local monitor、比對 `keyCode`（4 = H），
選單上只是顯示快捷鍵。

### 12.8 架構

**網頁端是標記資料的唯一真相，Swift 只負責讀寫檔與鏡像給側欄。** 合併、擦除、
錨點比對都需要渲染後的文字位置，只有網頁端拿得到；讓 Swift 持有模型的話，
這些邏輯最後還是得問網頁端，會分散在兩邊。

| 方向 | 介面 | 用途 |
|---|---|---|
| Swift → JS | `MB.render(markdown, {keepScroll, highlights})` | 換檔時同一次呼叫送進 sidecar 內容（含唯讀狀態），標記與內文同一個畫面出現；重載同一份文件不帶 `highlights`，沿用記憶體裡的 |
| Swift → JS | `MB.setHighlights(payload)` | sidecar 被外部改動、或認領孤兒之後重新載入 |
| Swift → JS | `MB.setHighlightBanner(text, actions)` | 警示列（12.9 節）；`null` 收起 |
| Swift → JS | `MB.revealHighlight(id)` | 側欄點一列 |
| Swift → JS | `MB.deleteHighlight(id)` | 側欄右鍵刪除 |
| Swift → JS | `MB.highlightSelection()` | `Shift Cmd H`；回傳有沒有建立，沒有就發提示音 |
| Swift → JS | `MB.commitNote()` | 視窗失去焦點、換檔、改名、關窗、結束前先把註記寫入；回傳寫入的內容，網頁端來不及送訊息時 Swift 自己寫 |
| Swift → JS | `MB.probeHighlights(candidates)` | 認領孤兒 sidecar 前試比對；回傳每份對得上幾條／總共幾條 |
| JS → Swift | `highlights` | 比對後的清單，側欄鏡像 |
| JS → Swift | `saveHighlights` | `{doc, json}`：完整 sidecar 內容或 `null`（刪檔）。帶著 `doc` 是因為換檔前最後一筆註記會晚一步到，要寫回它自己的 sidecar |
| JS → Swift | `copy` | 拷貝文字，走 `NSPasteboard` |
| JS → Swift | `bannerAction` | 警示列上的按鈕：重試、在 Finder 中顯示 |

需要回傳值的三個（`highlightSelection`、`commitNote`、`probeHighlights`）直接用
`evaluateJavaScript` 的完成回呼拿，不另外設計訊息。

**sidecar 也要監聽**：`git pull`、`git checkout` 會從外部改它。不另外掛一個檔案監聽
（sidecar 常常還不存在，`FileWatcher` 開不了檔就會一直重試），而是搭現有的資料夾
監聽 —— git 與 App 自己都是「寫暫存檔再 rename」，一定會反映在資料夾上。
App 自己寫檔也會觸發事件，所以收到事件先比對內容，跟最後一次讀到或寫入的一樣就忽略；
讀不出來的壞檔也記下原文，同一份壞檔不會反覆觸發。

### 12.9 寫不進去或讀不出來

| 情況 | 處理 |
|---|---|
| 資料夾不能寫（DMG、唯讀磁碟） | 開檔時檢查。工具列照樣浮出、拷貝能用，其他按鈕變灰，底下寫「此資料夾無法寫入，不能標記」；已有的 sidecar 照樣顯示 |
| 寫入失敗（磁碟滿、被鎖住） | 不跳對話框（註記每 500 ms 寫一次會連續轟炸）。內文頂端出現不擋操作的警示列與「重試」，標記留在記憶體、下次異動自動重試。**關視窗、換檔、結束 App 時還有沒寫進去的**才跳對話框：再試一次／拷貝為 JSON／放棄。這三個時機都要先等網頁端把最後一筆註記寫完（`commitNote` 的回呼）再判斷，否則最後一筆寫入失敗時對話框已經錯過 |
| sidecar 解析失敗、`version` 太新、或有看不懂的條目 | **一律唯讀，絕不覆蓋**。看不懂的條目（樣式不認得、欄位型別不對）網頁端載入時會略過，下一次存檔就等於刪掉它們，所以只要有一條就整個檔唯讀。git 合併衝突留下的 `<<<<<<<` 就是這種情況 —— 當作「沒有標記」的話，畫一條線就會把衝突檔連同兩邊的標記一起蓋掉。警示列寫明原因並附「在 Finder 中顯示」，修好後監聽偵測到改動就自動解除 |

不做備援位置（例如改存到 `~/Library/Application Support/`）：多一個存放地點就要處理兩邊合併。

### 12.10 改名

改名幾乎都是 AI 做的，三層處理：

1. **源頭**：`~/books/CLAUDE.md` 規定改 `.md` 檔名時，同名的
   `_highlights.json` 一起 `git mv`。
2. **App 開著時**：`FileWatcher` 收到 `.rename`，在重掛監聽之前用
   `fcntl(fd, F_GETPATH)` 問出還開著的 fd 現在的路徑。舊路徑沒有馬上又出現
   （排除編輯器「寫暫存檔再 rename 蓋過去」的原子存檔）、而且新路徑不在垃圾桶裡
   （丟進垃圾桶在檔案系統上也是一次 rename，跟過去的話 sidecar 會被搬進垃圾桶），就是真的改名：
   視窗跟到新檔，sidecar 一起改名。這是「只有使用者動作才寫檔」唯一的例外 ——
   它是在跟上一個已經發生的改名，比留下孤兒乾淨。順便修掉「改名後視窗卡在舊內容、
   每 0.3 秒重試開舊路徑」的舊 bug。
3. **App 沒開著時**：打開一個沒有 sidecar 的檔，掃**同資料夾**裡「對應的檔已經不存在」
   的 sidecar，拿它的 `exact` 試比對目前內容。**過半數**對得上就詢問
   「找到 12 條可能屬於這個檔案的標記（來自 `舊檔名`），要接上嗎？」，同意才改名接上。

### 12.11 列印

**不印標記也不印註記。** 列印與 PDF 輸出跟沒有標記時完全一樣：`print.css` 拿掉
`mark.mb-hl` 的底色、底線與註記圓點，工具列、tooltip、警示列一律隱藏。

## 13. EPUB 與對照閱讀

讀書寫心得時，書與心得要能並排對照。EPUB 在這個 App 裡有兩種身分：
**可以單獨閱讀的文件**（還沒寫心得的書也能讀），以及**心得的對照書**
（同一個視窗左書右心得，點標題互相跳轉）。

排版目標跟 `.md` 一樣：套同一套樣式、字體與外觀，**書裡的粗體也只換成橘色、不加粗**。

**不做**：書庫或書架、書目清單、跨書搜尋、有 DRM 的 EPUB、捲動連動（一邊捲另一邊跟著捲）、
書 → 心得方向的內文關鍵詞搜尋（13.6 節）。

### 13.1 開啟

- Finder 的「打開方式」裡有本 App，但**不搶 `.epub` 的預設程式**（第 8 節）
- `Cmd O`、最近開啟都能開 EPUB；最近開啟清單裡 EPUB 與 `.md` 混排
- **上次閱讀位置**記在 UserDefaults，以 EPUB 路徑為 key，存標題錨點（同 5.4 節的回位方式），
  固定版面存頁碼。不寫任何檔案
- 單獨開書時，側欄上半是空的，下半大綱顯示書的目錄（13.4 節的形式）
- `Cmd E`（用 MarkEdit 開啟）在焦點是書那欄時停用

### 13.2 書與心得的配對

**從心得找書**（開心得時）：

1. 從心得 h1 的《》取出書名。h1 可能是 `閱讀筆記：《書 B》進度`，所以只取《》裡面
2. 取**短書名**：切掉第一個「：」或「_」之後的部分
3. 從心得所在資料夾往上找，第一層含有 `.epub` 的資料夾就是書庫位置（現況是 `~/books/`）
4. 讀那層每本 EPUB 的 `dc:title`，同樣取短書名，相同就配對。都對不到就退回比對檔名的短書名

現有資料全部對得上：

| 書 | `dc:title` | 心得 h1 的書名 | 短書名 |
|---|---|---|---|
| 書 A | `書 A` | 書 A | 書 A |
| 書 B | `書 B` | 書 B | 書 B |
| 書 C | 書 C | 書 C | 書 C |
| 書 D | 書 D | 書 D | 書 D |

**手動指定**：比對不到或配錯（例如想對照英文原版）時，選單「檔案 → 指定對應書籍…」
選一本 EPUB，存在 UserDefaults，key 是心得**資料夾**路徑（同一本書的各章共用）。
手動指定優先於自動比對；選單另有「清除指定」。

**從書找心得**（從 Finder 單獨開書時）：在 EPUB 所在資料夾底下兩層內，找資料夾名稱或
`.md` 的 h1 短書名相符的心得；手動指定的對應也反查。找到就以雙欄開啟，心得欄開
**上次在那個資料夾讀的檔**；沒有紀錄就開書目前所在章對應的那份（13.6 節）；
再沒有就開 `ChapterSort` 排序的第一份。對照開關關著時一律單欄。

### 13.3 雙欄與 tab

同一個視窗、左書右心得。

- **對照開關**：每個視窗一個布林值，新視窗沿用最後一次的值（寫回 `AppSettings`），
  第一次安裝預設**開**。開著時，心得配對到書就自動切成雙欄；關著時不自動，按工具列
  「對照書籍」或 `Shift Cmd B` 打開。沒有配對到書時按鈕變灰
- 同一個視窗內換到同一本書的另一章：書留著，不重新配對
- **書剛被配對打開時停在哪裡**：上次讀到的位置就在這份心得的那一章，就回到那裡；
  否則（包括第一次打開）翻到心得這一章的章首。打開第 5 章的心得，要看的是書的第 5 章，
  不是封面，也不是上次讀到的第 3 章
- **分隔線可拖**，比例存成每個視窗的設定，新視窗沿用上次。預設 1:1
- **內容區小於約 1040pt**（兩欄各約 520pt 才不會讓中文行寬太短）時自動改成 tab，
  拖動視窗寬度時即時切換，切成 tab 時顯示剛才的焦點欄。tab 列在內容區頂端，`Ctrl Tab` 切換
- **焦點欄**：最後點過的那一欄。`Cmd F`、`Cmd P` 作用在焦點欄；字級兩欄共用同一個值
- 字體、外觀兩欄共用，都跟著視窗走

### 13.4 側欄與書的目錄

**側欄固定給心得用**：上半同資料夾的 `.md`，下半心得大綱或標記，跟現在一樣。
點了一下書，側欄也不換。

書的目錄放在**書那欄頂端的下拉選單**：

- 章節以 EPUB 的 nav（EPUB 3）或 `toc.ncx`（EPUB 2）為準，不以 spine 檔案為準 ——
  有些書一個檔裝兩章、或一章拆成兩個檔
- 下拉選單列全書的章；目前所在章展開它底下的小節，其他章收起。《書 A》的 h2
  是整句話，全攤開會很長
- 有對應心得的章，章名旁標一個小點；沒有的（還沒寫的章、注釋、謝辭）變灰，
  點了只捲書、不換心得

### 13.5 書的渲染（可重排 EPUB）

**整本串成一條**：依 spine 順序把所有 XHTML 接成一份文件，同步與 `Cmd F` 都不必處理跨章。
文字量約 0.5–1 MB，圖片 lazy load。

**樣式：先讀後丟。** 書的粗體大多不是 `<b>`：《書 A》用
`<span class="nls_BOLD">`，《書 C》用 `class_s495` 這種亂碼 class，只有
《書 D》用 `<b>`。丟掉書的 CSS 就連粗體一起丟了；保留書的 CSS 則粗體會真的加粗、
每本書長得都不一樣。所以：

1. 載入書的 CSS（只載入，不顯示）
2. 用 `getComputedStyle` 判斷每個元素實際上是不是粗體、斜體、置中、首行縮排、小字，
   轉成我們自己的語意標記（粗體一律走 `strong` 的樣式，也就是橘色、不加粗）
3. 卸掉書的 CSS，套我們的樣式

**方框**：四邊都有框線的區塊（《書 E》的「【第一類】（小節名）」、
《書 B》的「行動指引」、《書 A》章末的小故事）是作者刻意圈起來的，丟掉 CSS 就跟
內文分不出來。這類區塊標成 `mb-box`，用我們的框線色畫一個細框；顏色、粗細、圓角都不照書
（書是配白紙設計的）。框裡又有框只畫外面那個。翻頁模式下跨頁的框照樣斷開，前一頁沒有底線、
後一頁沒有頂線。

**偽標題**：有些書（calibre 轉出來的特別多）整本沒有標題標籤，章節標題是一段靠 CSS 加大
加粗的段落（《書 E》的 `<p class="titleinbig">`，1.29em）。書的 CSS 丟掉後只剩粗體，
變成橘色的普通文字，大綱是空的、同步也對不到。所以讀 CSS 時找出「短（80 字內、不以句號
結尾，問號不算 —— 「適合誰？」這種問句標題很常見）、加粗、字級比內文大一成以上」的段落，整本讀完後升格成真的標題。層級看書的目錄：
目錄指到的那幾個照目錄層級，同一種樣式（原本的 class）的其他段落跟它同一層，目錄沒指到的
樣式放在下一層。只用字級或出現次數排不可靠 —— 這本書有六種一樣 1.29em 的粗體樣式，小節
標題會被擠到最底層。書沒有目錄可對時，才依字級由大到小排。從 `h2` 開始（`h1` 留給書自己標的
章名）。依每本書的目錄與樣式自動算，不維護 class 對照表。

**副標**：書常把章名與副標用同一層標籤（《書 A》兩個都是 `h1`，靠 CSS 分 1.5em 與
1.1em）。書的 CSS 丟掉後兩個一樣大，所以同時比原書字級：同一章裡同層標題，比第一個小兩成
以上的就標成副標（`mb-subhead`），降一級顯示。

「從粗體改回一般」與「從置中改回靠左」也要轉：書常把 `<li>` 設成粗體只為了讓編號變粗，
裡面的段落再改回一般 —— 我們的粗體是顏色，顏色會往下繼承，不轉的話整個清單項目都變橘色。

**每一章只套它自己的樣式**：一章一章輪流在 iframe 裡套「這個 XHTML 連結的 CSS ＋ 它自己的
`<style>`」，不是整本一起套。《書 A》有一頁自帶 `<style>p{text-align:center}</style>`，
整本一起套就漏到全書每一段，清單、內文全部置中。

只認上面這一小組屬性，**不維護每本書的 class 對照表**（那會變成書庫管理）。
更花俏的版面（首字放大、底色框）會被攤平。書嵌的字型一律不用，字體跟著 `data-font`。

**書內連結**：串成一條時，各檔的 `id` 加上檔案前綴防撞，`href="ch3.xhtml#n12"` 改寫成
文件內錨點。目錄、注腳編號、注釋的返回連結都照常可點。

**注腳用浮框**：點注腳編號，在旁邊彈出小框顯示注釋內容，不動捲動位置（對照時跳走
再跳回，另一欄的同步關係會亂）。`<aside>` 只有在被 `epub:type="footnote|endnote|rearnote"`
標記、或有連結指向它時才從正文收起；其他 `<aside>`（拿來當側欄方塊的）照常顯示。
書末的注釋章本身保留，可以讀。

**圖片**：解析與讀 CSS 的那一步在一個看不見的 iframe 裡做，圖片在那裡**不能先載** ——
iframe 一拿掉，還沒載完的請求全部中斷、變成破圖（實測《書 D》101 張圖幾乎全破，
圖少的書剛好來得及所以看不出來）。所以先把位址存在 `data-mb-src`，搬進正式文件後才接上。
也不用 lazy load：圖片載入後才撐開高度，上方版面位移，同步與閱讀位置就落在錯的地方；
`width`／`height` 屬性保留，讓瀏覽器先用長寬比佔位。

**回位與版面位移**：字型與圖片晚到都會讓整本重新斷行。開書時回到閱讀位置之後，等圖片與
`document.fonts.ready`（最多 4 秒）再回位一次；同步捲到目標後 0.7 秒與版面穩定後各檢查一次，
偏了就再對齊。使用者這段期間自己捲動、按鍵、點擊過，或已經被同步帶到別處，就不再校正。

**欄寬改變時守住閱讀位置**（兩欄都適用）：拖分隔線、縮放視窗、切 tab 都會讓上方文字重新斷行，
WebKit 沒有 scroll anchoring，讀到的地方會整段漂走。捲動停下時記住畫面頂端的位置，
寬度一變就回到那裡；縮放過程中重排引起的捲動不算數。

**資源**：Swift 端用 ZIPFoundation 直接從 ZIP 串流讀單一檔案，走 `mbres://` 新增的
`book` 來源（跟 `app`、`doc` 並列）。這是專案第一個 SPM 依賴。
不先解壓到暫存資料夾：15 MB 的書解壓有延遲，暫存還要處理清理。

**自動重載**：沿用 `FileWatcher`。翻譯 repo 重新打包 EPUB 時，重載後用標題錨點回位、
標記重新比對（不寫檔），跟 `.md` 一樣。

**翻頁鍵**：捲動模式下 `←` 上一頁、`→` 下一頁。一頁是一個畫面高、留兩行重疊，
翻過去還接得上剛才讀到的地方。可重排的書一律橫排顯示，原書右翻左也不反過來。
焦點在書那欄才作用（在心得那欄按方向鍵照舊）。翻頁模式的按鍵見 13.12。

**不支援**：有 DRM 的 EPUB，開啟時顯示說明，不硬做。

### 13.6 同步

點一邊的標題，**另一邊**捲到對應位置；自己這邊不動。

**入口**：內文的 h1–h4、側欄大綱的項目、書的下拉選單都會帶動另一邊。拖選文字時
（選取範圍非空）不觸發，避免跟標記的操作打架。

**章對應以章名比對為主。** 《書 A》的 nav 沒有章號（只有「（章名）」），
光靠 `ChapterSort` 對不上；但心得開頭的引言都寫著書的章名：

```
> 第 3 章　（章名）
> 作者的話／前言：追尋簡單的生活
> 第一章　（章名）
```

把 nav 的每個章名，去掉「第 X 章」、空白與標點後，拿去比對心得的 h1、開頭引言、
各級標題（單檔心得如《書 D》的章名就在 h3）。一份心得可以對到多個 nav 項目
（「作者的話與前言」對到兩個）。比對不到才退回章號，章號由 `ChapterSort` 解析。

拿現有四本書實測後補上的規則：

- **同一個章名出現在好幾份的開頭，取章名佔那一行最多的那份**。全書總結的引言寫著
  「全書 21 章 ＋ 作者的話、前言。逐章心得見同目錄各檔」，不這樣排就把「作者的話」
  與「目錄」都搶走了
- **兩個字的章名**（「前言」「目錄」）太泛，只認 h1 結尾（「心得——前言」）
- **上層與下層對到同一份時留下層**：「第一部（部名）」寫在第一章心得的引言裡，
  留著它的話，還沒寫心得的第二章會往上找到第一部、跳去第一章的心得
- **上層已經對到的子項目不再比標題**：《書 D》的「3.1（小節名）」會被心得裡
  第 4 章的同名標題搶走。子項目一律往上找有對應的上層章
- 翻譯版本不同時章名常對不上（書是「（章名甲）」、心得是「（章名乙）」），
  單檔心得的標題寫著同一個章號也算

**章內用標題文字比對。** 心得的小節標題大多是自己下的，書裡沒有對應（《書 A》
第 3 章心得有 8 個標題，書只有章名加 2 個 h2）。所以：

1. 同一章內，兩邊標題去掉「一、」這類編號與標點，做前綴或包含比對
2. 對得到就捲到那個標題。好幾個都對得到時：完全相同 > 前綴 > 包含，同一級取重疊字數多的
3. 心得標題寫成「活出有使命的人生｜做個有用的人」（上層｜下層）時，先拿最後一段去比 ——
   整句比的話，章名「活出有使命的人生」是前綴，會贏過真正要找的小節
4. 對不到就捲到章首，並短暫提示「找不到對應小節，已跳到章首」。點的是章名本身
   （心得的 h1、書那一章的第一個標題）就不提示 —— 章首正是要去的地方

被帶動的那一邊捲到之後，目標標題**閃一下底色**（約 1 秒）。

**從書換心得**：點書的章名，心得欄換到那章的檔（單檔心得則捲到那章的標題）。
換檔一律走 `WindowRouter.open(_:in:)`，遇到目標檔開在別的視窗見 13.7 節。

**tab 模式**：點標題**不切 tab**，只在背景把另一個 tab 捲好；切過去時一樣閃底色。
tab 模式下看得到的只有一邊，點標題的意圖通常是在這邊導航。

**標題對不到時，用關鍵詞找內文**（只有心得 → 書）：心得的小節標題大多是自己下的，
書裡沒有對應的標題，原本點了幾乎都退回章首。所以標題比對失敗後，拿心得標題去書的那一章
內文找：

1. **關鍵詞**是心得標題與該章內文的**最長重疊字串**，至少 3 個字（標題先去掉「一、」編號與
   標點）。頭尾是虛詞（的、了、與、是、在、和、就、也、而、或、及、之、把、被、讓、不、個、成）的不算，
   找次長的 —— 「的結果」「同一個」「記住的」這類只是虛詞組合，照著跳會落在不相干的段落
2. 關鍵詞在那一章出現好幾次時，跳到**第一次出現**的地方（書第一次提到一個人名或故事，
   幾乎都是那段的開頭）
3. **呈現**：捲到（翻頁模式翻到）那個段落，**只閃關鍵詞本身**，同時短暫提示
   「依關鍵詞「普魯斯特」對到內文」—— 這是推測，跳錯時才知道不是標題直接對到。
   不留底色，免得跟自己畫的標記搞混
4. 關鍵詞也對不到，才退回章首並提示「找不到對應小節」

搜尋範圍跟標題比對相同（一份心得對到兩章就兩章都找），被收起來的注腳不算。點的是章名
（心得的 h1、單檔心得裡那一章的章名標題）就不找，照舊到章首。tab 模式照樣在背景捲好、
切過去才閃。固定版面沒有文字可搜，不適用。書 → 心得不做：心得是在摘要書，書的標題對不到
時，心得裡多半也沒有一模一樣的字。

拿《書 A》6 章、62 個心得標題試算：最長重疊字串（至少 3 字）找得到 48 個，扣掉
虛詞組合約 40 個可用，其餘是「全章總結」「心得」這類自己的結構性標題，書裡本來就沒有。

**點引文，找書的原句**（只有心得 → 書）：心得的引文（`>`）多半一字不差抄自書。點引文裡的
一段（一個段落或清單項目，不是整塊 —— 同一塊常連引好幾句），書就捲（翻）到那句原文，
閃那一段字。

1. 兩邊都拿掉空白與標點、全形半形歸一、異體字歸一（書常用「爲」「着」「裏」）再比
2. 引文就是目錄上的章名（心得檔頭的「第4章：…」）就到那一章章首。《書 E》的
   章首是一張圖，正文裡同樣的字只出現在書末的參考文獻
3. 先找引文所在小節對應的章（單檔心得照標題同步的規則往回找章名）：完整出現，或最長的
   一段重疊（至少 8 個字、也至少佔引文四成），部分對到時提示「書裡沒有完全相同的句子，
   已跳到最接近的一段」。這一章都沒有才找全書 —— 引文可能出自別章，也可能在第一個標題之前、
   對不到章。連全書也沒有就提示「書裡找不到這段引文」
4. 引文一段裡有好幾行（`>` 連續幾行不空行，檔頭的章名與作者就是）時，只找點到的那一行
5. 完整對到不提示。拖選文字、點標記、點連結不觸發；tab 模式照樣在背景翻好、切過去才閃
6. 對照中滑到引文上游標變成手指，讓人知道可以點；沒在對照時維持一般游標。凡是點了會帶動
   另一欄的都一樣：兩欄內文的 h1–h4、側欄的大綱與書的目錄。只開書但對照開關開著時，
   書的標題也算（點了會帶出那章的心得）

固定版面沒有文字，退回翻到那一章。拿《書 E》序到第 4 章 47 行引文試算：完整
對到 44 行，沒對到的 3 行是自己加註的副書名與公式。

### 13.7 一檔一窗延伸到 EPUB

書也能標記（13.8 節），所以 11.2 節的一檔一窗同樣適用於 EPUB：同一本書只開在一個視窗裡。
**原則是對照組（書＋心得）往你正在操作的視窗集中。**

| 情境 | 處理 |
|---|---|
| 配對到的書已開在另一個視窗 | **搬過來**：書從那個視窗撤走（變回單欄），在這個視窗打開。自動配對與手動按按鈕都一樣 |
| 從書跳到某章心得，那份心得開在另一個視窗 | **搬過來**：心得從那個視窗撤走；那個視窗因此空了就**自動關閉** |
| 同上，但那個視窗的心得另外配了別本書（手動指定） | 不搬。只捲書，提示「那章的心得開在其他視窗」 |

搬動或關窗前，被撤走的那一邊如果有開著的註記框，**先 `commitNote` 寫完再搬**，
寫入失敗照 12.9 節跳對話框。被撤走的書，閱讀位置跟著帶過來。

### 13.8 書的標記

規則完全比照第 12 節，差異只有：

- sidecar 在 EPUB 旁邊：`<EPUB 檔名去掉副檔名>_highlights.json`，跟心得的 sidecar 分開
- `heading` 是書內標題的 slug（含 13.5 節的檔案前綴）
- 錨點比對的範圍是整本串成一條之後的渲染文字
- 書被重新打包（例如修訂譯文）後對不上的，照 12.5 節列入「找不到位置」
- 側欄的「標記」分頁先列心得、再列書的標記，各自依所在標題分組，分頁上的數字是兩者總數。
  點書的那幾條，書那欄捲（翻）到那裡並閃一下。原本只列心得的，結果書裡畫了再多，分頁上也寫
  「標記 0」，看起來像沒存到

`~/books/CLAUDE.md` 目前只規範心得旁的 `_highlights.json`，EPUB 旁的 sidecar
要另外補一條（同樣不跟 EPUB 混在同一個 commit）。

### 13.9 固定版面 EPUB

OPF 宣告 `rendition:layout` 為 `pre-paginated` 的書。現有 14 本全部是可重排的，
所以這部分只做最小支援：

- **翻頁式顯示、等比縮放**，記住頁碼（13.1 節）
- **不套我們的樣式、不能標記**：每頁是絕對定位的排版、常常整頁是一張圖，13.5 節的
  轉換與第 12 節的錨點都做不了
- **跨頁**：聽書那欄頂端的「捲動｜單頁｜雙頁」（13.12）。選雙頁才並排兩頁，「捲動」對固定版面
  沒有意義，當作單頁。書那欄寬度不夠（單頁會小於約 400pt）就暫時退回單頁。書宣告
  `rendition:spread="none"` 的永遠單頁。封面單獨一頁，之後兩兩成對
- 每頁是一個 `mbres://book/` 的 iframe，`pointer-events: none`，鍵盤與觸控板翻頁留在外層。
  視窗縮放時只改尺寸、不重建 iframe（重建會整頁閃白）
- **翻頁方向**照 `page-progression-direction`（直排書右翻左）決定跨頁裡哪頁在左、
  觸控板往哪邊滑是下一頁。空白鍵下一頁、`⇧` 空白鍵上一頁
- **方向鍵跟著畫面走**：左翻右的書 `←` 上一頁、`→` 下一頁；右翻左的書反過來，
  `←` 前往左邊那頁（下一頁），跟紙本與漫畫閱讀器一樣

**同步只到章**（沒有文字標題可點，也沒有小節可比對）：

- 心得 → 書：章名比對（13.6 節）找到 nav 的那一章，翻到起始頁；頁碼指示閃一下
- 書 → 心得：下拉選單選章；另外，**翻頁跨過章界時，心得自動換到那章**。翻頁是離散事件，
  不像捲動會一直觸發。換過去時目標心得在別的視窗，照 13.7 節搬過來

### 13.10 架構

| 方向 | 介面 | 用途 |
|---|---|---|
| Swift → JS | `MB.renderBook(manifest, {position, highlights})` | 書那欄的網頁端載入整本書；`manifest` 是 spine、nav 與資源路徑 |
| Swift → JS | `MB.renderBookError(text)` | 讀不出來、有 DRM |
| Swift → JS | `MB.syncTo(request)` | 被帶動的一邊捲到對應位置並閃底色；對不到小節由網頁端自己提示。心得那欄的 `request` 帶 `scope`（單檔心得那一章的標題）與 `text`，書那欄帶 `chapters` 與 `text`（點引文時改帶 `quote`）；`background` 為真是 tab 模式下看不到的那欄 |
| Swift → JS | `MB.scrollToChapter(index)` | 書的下拉選單選了某一章 |
| Swift → JS | `MB.revealPendingSync()` | 切到背景捲好的那個 tab 時，才閃目標標題 |
| Swift → JS | `MB.setLinked(on)` | 這一欄點標題（心得那欄還有引文）會不會帶動另一欄，決定游標要不要變手指 |
| Swift → JS | `MB.toast(text)` | 「這一章還沒有心得」之類的短暫提示 |
| JS → Swift | `headingClicked` | 內文標題被點，Swift 轉給另一欄；書那欄另帶所在章與「是不是章名」 |
| JS → Swift | `quoteClicked` | 心得引文裡的一段被點，帶文字與所在小節的標題 id，Swift 算出章再叫書那欄找原句 |
| JS → Swift | `bookPosition` | 書目前所在章與位置，給下拉選單、閱讀位置記憶與固定版面的跨章換心得。剛渲染完只報章、不帶位置 —— 版面還沒穩，存下來的會是錯的 |
| JS → Swift | `focus` | 任何 mousedown，決定焦點欄 |

換心得檔之後的同步（`syncTo`）要等新檔渲染完：`PaneDocument.queueSync` 先存著，
`render` 送出內容之後才送。新開的欄網頁端還沒載入完也一樣等。

兩欄各是一個 `WKWebView`，各自一個 `WebPane.Coordinator`。**兩欄之間不直接溝通**，
一律經過 Swift 轉送：章名對應、換心得檔、搬視窗都需要 `WindowRouter` 參與。
章名對應表在 Swift 端算（需要讀心得資料夾裡的其他檔），渲染後的標題比對在網頁端做。

狀態的切法：文件本身（讀哪個檔、大綱、標記、sidecar、檔案監聽、關窗前寫完註記）抽成
`PaneDocument`，心得（`DocumentState` 本身）與書（`BookPane`）各一份，所以書的標記與心得
走的是同一段程式，不是複製一份。`DocumentState` 另外持有視窗層級的東西：字體、
外觀、字級、對照開關、分隔線比例、焦點欄，以及 `book`。對照開關與分隔線比例照現有規則
用 `didSet` 寫回 `AppSettings` 當新視窗的起始值。

兩個 `WebPane` 在版面裡永遠留在同一個位置，切雙欄、切 tab、拖分隔線只改大小與透明度 ——
視圖結構一變，SwiftUI 就重建 WKWebView，捲動位置、搜尋、打到一半的註記全部消失。

### 13.12 翻頁模式（可重排 EPUB）

捲動模式之外，書那欄多一種一般電子書的翻頁模式：上下左右都留白，一次翻一整頁，
翻頁前後**文字不重複**。心得那欄一律維持捲動 —— 心得會被 AI 改寫而自動重載，
翻頁模式下的回位會變成「回到第幾頁」，頁碼一重排就跑掉。

**切換**：書那欄頂端，章節下拉選單右邊一個三選一「捲動｜單頁｜雙頁」；選單列
「顯示方式 → 書：捲動／單頁／雙頁」同樣是三選一。不配快捷鍵。設定是每個視窗各自，
新視窗沿用最後一次的選擇；第一次安裝預設**單頁**（翻頁模式）。

**單頁與雙頁**：使用者自己選，不自動判斷。選了雙頁但書那欄窄到每頁不足約 30 字，
就**暫時**顯示單頁，設定仍記著雙頁，欄寬回來自動恢復（例如開了對照，書那欄只剩半個視窗）。

**版面**：

- 一頁的寬度照 4.6 節「滿版、只留固定左右內距」的規則，不另設行寬上限 —— 太寬就自己切雙頁
- 上下左右都留白，比例參考 Apple 書籍：頁緣與內文之間的空白明顯寬於捲動模式
- **每一章從新的一頁開始**，章的邊界是 spine 檔（一個 XHTML 一個分頁單位）
- 雙頁時新的一章**緊接著用下一個空頁**：上一章結束在左頁，下一章就從右頁開始，
  不留整個空跨頁，也不強求章首在右頁 —— 雙頁只是暫時狀態，頁面位置本來就會重排

**封面與書名頁滿版**：只有一張圖、沒有文字的章（封面、書名頁），翻到時圖從頁面頂端放到底部，
不受上下留白限制；雙頁時只佔那一側。多欄版面裡的圖撐不出上下留白（容器上下不能有 padding，
見「做法」），所以停在這種頁面時另外蓋一層顯示；翻頁滑動中先拿掉，滑動時看到的是版面裡
原本的圖。

**頁碼**：底部留白裡的淡色小字，左下角「本章 x／y 頁」對齊內文左緣，右下角全書百分比
「49%」對齊內文右緣。雙頁時兩者分別在整個跨頁的左下、右下兩個外側角落。

- 「本章」以 spine 檔為單位，跟換新頁的邊界相同。一個檔裝兩章的少數書，頁數兩章合算
- 百分比以**全書文字的位置**計算，不用頁數。頁數會隨字級、欄寬、單雙頁改變，
  用字數算的話，同一個位置不管怎麼排版百分比都一樣

**翻頁方式**：

| 操作 | 下一頁 | 上一頁 |
|---|---|---|
| 鍵盤 | `→`、空白鍵、`PageDown`、`↓` | `←`、`⇧` 空白鍵、`PageUp`、`↑` |
| 觸控板與滾輪 | 往左滑、往下滾 | 往右滑、往上滾 |
| 滑鼠 | 點右側留白 | 點左側留白 |

- `Home`／`End` 跳到本章第一頁／最後一頁
- 觸控板與滾輪累積到門檻才翻一頁，翻完冷卻一下，跟固定版面同一套做法
- 左右兩側的留白區可以點：滑鼠移過去時出現淡淡的 ‹ ›，點了翻頁。內文區域的點擊
  照舊（選字畫標記、點標題同步、點注腳）—— 點內文左右半邊翻頁會跟這些打架
- 翻頁有約 0.2 秒的水平滑動，連按幾次時才分得出有沒有翻過去。不做仿紙張捲頁：
  在 WKWebView 裡做不好，還會干擾選取文字
- 方向一律 `→` 是下一頁（可重排的書一律橫排顯示）；右翻左的規則只適用於固定版面（13.9）

**跨頁的標記**：一句話被切在頁尾時，翻頁前後分兩次標，靠 12.2 節「緊接著的同色標記
也合併」連成一條。不做「拖曳選取到頁緣時自動翻頁」：在多欄排版裡做不穩，拖曳中翻頁
常讓選取範圍亂掉。

**其他功能在翻頁模式下的行為**：

- **同步**：被帶動到書時，翻到目標標題所在的那一頁，再閃一下標題。翻頁模式沒辦法讓標題
  剛好在頁首，頁面切在哪裡是排版決定的
- **閱讀位置**：照樣記「讀到的元素」，回來時翻到包含它的那一頁。不記頁碼
- **重新分頁**：切換捲動／翻頁、改字級、縮放視窗、拖分隔線、單雙頁自動退回時都會重排，
  停在包含原本位置的那一頁
- **搜尋**（`Cmd F`）：跳到下一筆時，自動翻到那一頁
- **注腳浮框、點標題同步、點標記**：行為不變
- **列印**：一律用捲動的版面輸出，翻頁模式不影響列印
- **書的下拉選單、側欄目錄**：選了某一章，翻到那一章的第一頁

**做法**：CSS 多欄排版，一欄就是一頁。欄距是左右留白的兩倍，所以單頁時一欄＋欄距、
雙頁時兩欄＋兩個欄距都剛好一個畫面寬，翻頁就是橫向移動一個畫面寬，文字天生不會重複。
整本是同一段多欄內容，每個 spine 檔的 section 設 `break-before: column`，章首自然落在
下一個空頁（雙頁時可能是右頁）。

橫向捲動的是 `#content` 自己（`scrollLeft`），不是整份文件 —— 根元素設了
`overflow: hidden` 之後，WebKit 不讓文件橫向捲動，`window.scrollTo` 不會有反應。
所有跳轉（同步、大綱、搜尋、標記、注腳連結）都走 `app.js` 的 `reveal()`：翻頁模式
是「翻到元素所在的那一頁」，捲動模式才是 `scrollIntoView`。

**多欄容器上下不能有 padding**：WebKit 算分頁高度時會把上下 padding 再扣一次，排版用的
頁高比畫出來的頁矮一截（實測 751 的頁只排到 623）。症狀是頁尾出現切掉一半的殘字（下一頁
開頭那一行被畫進這一頁底部），段落中間也會冒出一行空白（排版以為那裡是頁界）。所以頁高
直接設成扣掉上下留白後的值，上方留白用 margin 推下來；左右留白才用 padding。
另外設 `orphans: 1; widows: 1`，段落可以在任何一行斷頁，頁面用得比較滿。

**被推走的第一行會留下殘影**（WebKit 的繪製問題）：段落開頭剛好落在頁尾、放不下一整行時，
第一行被推到下一頁，上一頁底部卻仍畫出那一行的一截（連首行縮排都看得到）。排版後偵測
「方框在上一頁不到一行高」的區塊，加上 `break-before: column` 讓它直接從下一頁開始。那一行
本來就在下一頁，排版結果不變、後面也不會位移。用裁切擋不乾淨：殘影與正常的最後一行可能
重疊。版面每次改變（字級、欄寬、單雙頁、圖片與字型載入）都先拿掉舊標記再重新量。

**頁寬要用小數**：書那欄的寬度常是小數（818.75），`clientWidth` 會四捨五入成 819。用整數
當頁寬，每頁差 0.25px，翻到第 80 頁就累積 20px，元素被算進前一頁（同步翻到錯的頁、滿版圖
蓋住正文）。所以頁寬取 `getBoundingClientRect().width`，判斷元素在第幾頁也以「目前這一頁」
為基準往前後算，不從第一頁累加。

**滿版圖那一頁不能剛好等於欄高**：欄高常是小數，剛好 100% 會被進位擠出一頁空白。高度留
4px 餘裕，並設 `overflow: hidden` 讓它不可分割（圖旁常有只放 `<br>` 的空段落）。

閱讀位置除了「元素＋偏移」，另外記「第幾個 spine 檔的第幾個字」（`sec`／`off`）。
書裡的段落多半沒有 id，往上找會找到整章的 section；翻頁模式要知道在哪一頁、
捲動與翻頁互相切換時要回到同一個地方，都只能靠文字位置。
不把內容拆成一頁一頁的 DOM：那樣標記、搜尋、錨點比對都要跨頁處理，現有的
`highlights.js` 與搜尋會全部要改。
