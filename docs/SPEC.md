# MarkdownBrowser 規格

原生 macOS Markdown 閱讀器。目標是把 Claude Code 在 cmux／ghostty 裡的中文閱讀體驗，
搬到一個能雙點擊開啟、能列印、能自訂樣式的 App 裡。

版本：v1
日期：2026-09-11

---

## 1. 為什麼要有這個 App

陪讀電子書的流程會產出大量繁體中文心得 Markdown（`~/books/心得/`，
一本書一個資料夾、一章一個檔，13–27 KB）。這些檔案在終端機裡讀起來很好，
但匯入 Notion 或用 MarkEdit Preview 看都失真，關鍵失真點是**粗體**：

終端機的做法是 `ghostty/config` 裡這一組設定 ——

```
font-family = "SF Mono"
font-family = "LXGW WenKai Mono TC"
font-family-bold = "SF Mono"
font-family-bold = "LXGW WenKai Mono TC Light"
font-synthetic-style = no-bold
bold-color = #DD9853
```

也就是：**中文粗體不加粗，只換成橘色**。中文字加粗會糊成一團，
所以重點訊號完全交給顏色。一般 Markdown viewer 把 `**粗體**` 渲染成
`font-weight: bold`，中文就糊了，而且沒有顏色差，整頁看起來一片平。

v1 要重現的就是這件事，外加一套排版比終端機更好的閱讀主題。

## 2. 不做什麼

- 不做編輯。這是唯讀的閱讀器，要改內容用 `Cmd+E` 丟給 MarkEdit。
  標記與註記（第 12 節）不算編輯：它們寫進同資料夾的 sidecar 檔，**永遠不碰 `.md` 本身**。
- 不做書庫管理。沒有資料庫、沒有索引、沒有標籤。
- 不做 Mermaid、不做 KaTeX。各自要背一個幾百 KB 的 JS 引擎，而現有心得檔一個都沒用到。

## 3. 架構

```
SwiftUI（視窗、選單、Finder 關聯、檔案監聽、側欄）
        │  postMessage / evaluateJavaScript
        ▼
WKWebView（內容區，一個視窗一份）
        │
        ├── markdown-it 14.x（內嵌，vendored，不走網路）
        ├── base.css ＋ themes/{terminal,reading}.css
        └── 內嵌 LXGW WenKai TC / LXGW WenKai Mono TC
```

Swift 端只做「殼」——開檔、監聽、選單、側欄資料。所有排版都在 CSS 裡，
所以「兩套主題」只是換一個 `<html data-theme>` 屬性。

Swift 端的狀態分三份（多視窗的緣故，見第 11 節）：

| | 範圍 | 內容 |
|---|---|---|
| `DocumentState` | 一個視窗一份 | 讀哪個檔、側欄、主題、字體、字級、外觀 |
| `AppSettings` | 全 App | 新視窗的起始設定、最近開啟、自訂主題目錄 |
| `WindowRouter` | 全 App | 哪些視窗開著、哪一個在前景、下一個檔案開到哪裡 |

- 專案：`~/workspace/MarkdownBrowser`
- Bundle ID：`com.thomashsieh.markdownbrowser`
- 最低系統：macOS 14
- 建置：`Package.swift` ＋ `Makefile`，不用 `.xcodeproj`（pbxproj 難以手改與 review）

## 4. 主題

### 4.1 共通不變量

**粗體永不加粗。** `strong` 一律 `font-weight: normal`，改上 accent 色。
`-webkit-font-smoothing` 與 `font-synthetic-weight: none` 都要明確關掉合成粗體，
否則 WebKit 會替沒有 Bold 字面的字型合成假粗。

從截圖取樣得到的實際顏色：

| 用途 | 值 | 來源 |
|---|---|---|
| 背景 | `#1C1C1C` | 截圖取樣 |
| 內文 | `#CECECE` | 截圖取樣 |
| 重點（粗體） | `#DD9853` | `ghostty/config` 的 `bold-color` 宣告值 |
| 引言左側直線 | `#757575` | 截圖取樣 |
| 標題（閱讀主題） | `#A2D2FC` | MarkEdit 編輯區標題色，截圖取樣 |
| 框線 | `#CECECE`（終端機）／`#3A3A3A`（閱讀） | 終端機的 box-drawing 就是內文色 |

### 4.2 終端機主題（`terminal`）

盡量貼近截圖。

- 中文 `LXGW WenKai Mono TC`，英數 `SF Mono`
- 標題與內文**同字級**，標題上 accent 色（終端機沒有字級可用，只能靠顏色分層）
- 表格：等寬字，框線用 CSS `1px` 細線而不是 box-drawing 字元。
  真對齊要自己算雙寬字元寬度、自己折行、自己補空白，是整個專案裡最貴的一塊，
  而畫面差別只在框線粗細
- 行內程式碼與內文同色，只換等寬字面

### 4.3 閱讀主題（`reading`，預設）

排版重做，但視覺語言不變。

- 中文、英數全部用 `LXGW WenKai TC`（比例版，自帶拉丁字），開 `tabular-nums`
  讓表格裡的金額縱向對齊
- 標題靠**字級**分層，顏色一律 `#A2D2FC` 淺藍（取樣自 MarkEdit 編輯區的標題色），
  不上橘色 —— 全篇只有粗體是橘的，重點詞才保有唯一性。藍與橘色相離得夠遠，
  標題與重點詞不會互相混淆
- 行內程式碼仍走 `SF Mono`
- 行高 1.9

### 4.4 外觀：深色／淺色（與主題正交）

第三個獨立的軸。主題決定版面、字體決定用哪套中文字、外觀決定明暗那一組顏色。
選單在「顯示方式 → 外觀」，比照 Safari：**自動**（跟隨系統）／**淺色**／**深色**。

**淺色不是把深色反過來。** `#DD9853` 是為深色底調的橘，放到暖白紙上對比只有
**2.28:1**，遠低於內文需要的 4.5:1。所以淺色維持同一個色相、往下壓到通過
WCAG AA 為止：

| 用途 | 深色 | 淺色 | 淺色對比 |
|---|---|---|---|
| 背景 | `#1C1C1C` | `#FAF8F3`（暖白紙，純白對楷體長文偏刺眼） | — |
| 內文 | `#CECECE` | `#2A2A2A` | 13.5:1 |
| 重點（粗體） | `#DD9853` | `#A2541A` | 5.2:1 |
| 標題（閱讀主題） | `#A2D2FC` | `#2C5C8A` | 6.6:1 |

實作上，淺色覆寫寫在**各自的主題檔裡**（`:root[data-theme="X"][data-appearance="light"]`），
不是集中在 base.css —— 這樣一個主題檔仍然自給自足，自訂主題複製一份就能改。

兩個踩過的坑：

- 強制淺色／深色時要設 `NSWindow.appearance`，否則只有網頁內容變色，
  視窗外框（側欄、工具列、標題列）還是系統的。設在 `NSApp` 也有效，
  但那是全 App 的，一個視窗切淺色會把所有視窗一起拖下去 —— 外觀是
  每個視窗各自的（第 11 節），所以要設在視窗上。
- 跟隨系統時**不要用 KVO 盯 `NSApp.effectiveAppearance`** —— 它不保證 KVO
  相容，實測系統切換時不會觸發，結果是側欄自己變淺了、網頁內容還留在深色。
  要聽系統廣播的 `AppleInterfaceThemeChangedNotification`。

### 4.5 字體（與主題正交）

中文字體是獨立於主題的第二個軸。主題決定顏色與版面，`data-font` 只決定用哪套中文字：

| | 楷體 `kai`（預設） | 黑體 `gothic` |
|---|---|---|
| 比例（閱讀主題） | LXGW WenKai TC | Sarasa Gothic TC |
| 等寬（終端機主題） | LXGW WenKai Mono TC | Sarasa Mono TC |

`base.css` 把這兩組寫成 `--cjk` / `--cjk-mono`，主題檔只引用變數。
自訂主題想跟著切換，`font-family` 寫 `var(--cjk)` 就好。

**黑體的粗體也不加粗。** `switch-font.sh` 的 gothic profile 在終端機裡是把粗體
升到 SemiBold 的，這裡刻意不跟 —— 兩套字體的行為要一致，粗體永遠只換色，
否則「粗體長什麼樣」會隨字體而變。實作上是 `@font-face` 只帶 Regular、
字重範圍開成 `100 900`，任何字重請求都落回同一個字面。

### 4.6 行寬

**隨視窗滿版**，只留固定左右內距（`3rem`），不設 `max-width`。
`Cmd +` / `Cmd -` 調字級，`Cmd 0` 重設。

## 5. 功能

| 功能 | 快捷鍵 | 說明 |
|---|---|---|
| 開新視窗 | `Cmd N` | 空白視窗，接著 `Cmd O` 或從側欄挑。Dock 圖示的右鍵選單也有 |
| 開檔 | `Cmd O` | 換掉目前視窗的內容。Finder 雙點擊走另一套政策，見第 11 節 |
| 最近開啟 | — | 檔案選單的子選單，最多 10 筆，自己存在 UserDefaults |
| 切主題 | `Cmd 1` / `Cmd 2` | 閱讀／終端機。每個視窗各自，新視窗沿用最後一次的選擇 |
| 切字體 | `Cmd 3` / `Cmd 4` | 楷體／黑體。同樣是每個視窗各自 |
| 切外觀 | — | 自動／淺色／深色。同樣是每個視窗各自 |
| 調字級 | `Cmd +` `Cmd -` `Cmd 0` | 每個視窗各自，最後一次的值存進 UserDefaults |
| 側欄 | `Cmd \` | 可收合，每個視窗各自 |
| 搜尋 | `Cmd F` | 全部命中高亮、顯示第 n／共 m、Enter 下一筆、Shift-Enter 上一筆 |
| 用 MarkEdit 開啟 | `Cmd E` | `NSWorkspace.open(_:withApplicationAt:)` |
| 列印／PDF | `Cmd P` | 白底黑字，粗體轉淺色模式那個 `#A2541A` |
| 重新載入 | `Cmd R` | 手動；平常靠自動重載 |
| 標記選取文字 | `Shift Cmd H` | 選取範圍直接套綠色；平常是選取後點浮動工具列，見第 12 節 |

### 5.1 工具列

由左到右：側欄開關、**調色盤（主題與外觀）**、字體、字級加減、搜尋、
用 MarkEdit 開啟、列印。每個都給 `Label`（圖示＋標題），
使用者右鍵可以自己切換要不要顯示文字。

主題與外觀共用調色盤那一顆，用 `Divider()` 分成上下兩段 —— 分類上合理
（調色盤＝所有視覺設定），但**位置不明顯**，第一次找會找不到。
若之後要拆，選項是獨立一顆太陽／月亮按鈕，或補上快捷鍵
（`⌘1`–`⌘4` 已被主題與字體佔用）。

### 5.2 最近開啟

自己維護，不靠 `NSDocumentController` —— 這不是文件型 App，
系統那份清單管不到筆數上限，也不會把已刪掉的檔剔除。
存 10 筆路徑在 UserDefaults，載入時過濾掉已不存在的檔。

### 5.3 側欄

兩段式，上下同時顯示：

- **上半：同資料夾的 `.md`**。排序解析檔名裡的「第X章」，
  中文數字（一二三四五六七八九十）與阿拉伯數字都認；
  抽不出章號的（`附錄與後記`）排到最後，彼此之間按檔名。
  這是必要的 —— 字典序下 `第一章 / 第三章 / 第二章` 就是這個順序，
  兩個現有資料夾都亂掉。
- **下半：本文大綱**。`h1`–`h4`，點擊捲到該標題，捲動時高亮目前位置。

### 5.4 自動重載

用 `DispatchSource.makeFileSystemObjectSource` 監聽 `.write`／`.rename`／`.delete`，
去抖 150 ms。編輯器多半是「寫暫存檔再 rename」，所以 `rename`／`delete` 之後
要重新開 fd 重新掛監聽，否則只會收到一次事件。

重載後捲軸回原位：記下重載前**視窗頂端往下第一個標題的 id 與其偏移量**，
重載後找同 id 的標題捲回去。比純像素位置穩 —— AI 在你上方插入一段，
像素位置就整個位移了。

### 5.5 自訂主題與字型

```
~/.config/markdownbrowser/
  themes/*.css     每個檔就是一套主題，自動出現在「主題」選單
  fonts/*.ttf      自動註冊成 @font-face，family 名 = 檔名（去副檔名）
```

內建兩套主題用**完全相同的格式**，可以直接複製出來改。
選單裡提供「開啟設定資料夾」與「把內建主題複製一份出來」。

自訂主題檔在 App 啟動時掃描一次，並持續監聽該資料夾 —— 改了 CSS 立刻生效。

## 6. Markdown 語法

markdown-it 預設 CommonMark ＋ 打開 GFM 需要的：`tables`、`strikethrough`、
`linkify`。`html: false`（心得檔沒有原生 HTML，關掉比較安全）。

圖片支援本機相對路徑。網頁不是用 `file://` 載入的，而是自訂 scheme `mbres://` ——
`loadFileURL(_:allowingReadAccessTo:)` 只能開放一個目錄樹，但同時要讀三個
不相干的地方：App 自己的網頁資源、目前文件所在資料夾（相對路徑圖片）、
以及 `~/.config/markdownbrowser/fonts`。

    mbres://app/…       → Contents/Resources/web/…
    mbres://doc/…       → 目前文件所在資料夾
    mbres://userfont/…  → ~/.config/markdownbrowser/fonts

渲染後由 JS 把相對路徑的 `img[src]` 改寫成 `mbres://doc/…`，否則它會相對於
頁面位址解析到 App 自己的資源目錄去。handler 會擋掉用 `../` 逃出根目錄的請求。

外部連結（`http`/`https`）用 `NSWorkspace` 丟給預設瀏覽器，不在 App 內導航。

## 7. 字型

內嵌進 `.app`，每套只需要 Regular 字面（粗體靠顏色，不靠字重）：

| 檔案 | 大小 | 用途 |
|---|---|---|
| `LXGWWenKaiTC-Regular.ttf` | 13 MB | 楷體・比例 |
| `LXGWWenKaiMonoTC-Regular.ttf` | 13 MB | 楷體・等寬 |
| `SarasaGothicTC-Regular.ttf` | 24 MB | 黑體・比例 |
| `SarasaMonoTC-Regular.ttf` | 26 MB | 黑體・等寬 |

成品 `.app` 約 73 MB，絕大部分是字型。

**不進版控。** `make` 時依序找 `~/books/fonts/` →
`~/Library/Fonts/` → 官方 GitHub release 下載到 `.cache/fonts/`。

兩個踩過的坑：

- 比例版 `LXGWWenKaiTC-*` 沒裝在系統，只在 `books/fonts/` 裡；等寬版兩處都有。
- Sarasa 官方**只提供 7z**，而且要整個家族一包（約 60 MB）才拿得到那一個字面，
  所以下載那條路需要 `7z`（`brew install p7zip`）。系統裡那份 Sarasa 是
  832 MB 的 `.ttc` 集合檔，拆不出單一 TTF，幫不上忙。

## 8. Finder 關聯

`Info.plist` 的 `CFBundleDocumentTypes` 宣告 `net.daringfireball.markdown`、
`public.markdown` 與副檔名 `md`/`markdown`/`mdown`/`mkd`，
`LSHandlerRank` 設 `Owner`，角色 `Viewer`。

`.mdown`／`.mkd`／`.mdwn` 另外宣告一個本 App 擁有的類型
`com.thomashsieh.markdownbrowser.markdown-variant`（`UTExportedTypeDeclarations`，
掛在 `net.daringfireball.markdown` 底下）。只在匯入的 `net.daringfireball.markdown`
裡多列這三個副檔名沒有用：匯入宣告的優先序最低，那個 UTI 已經有更權威的宣告，
多列的副檔名被忽略，三者變成動態類型，實測被 Notion、VS Code 搶走。

`public.markdown` 雖然列在 `LSItemContentTypes` 裡，但 `make set-default` 不設它：
它在系統上是個沒有上層類型的空殼，沒有任何副檔名對應到它，`NSWorkspace` 與
LaunchServices 都拒絕替它設預設程式，設了也不影響任何檔案。

`Info.plist` 裡宣告 `Owner` 只代表「我有能力開」，不等於預設程式 ——
真正的預設是使用者層級的設定。`make set-default` 會呼叫
`NSWorkspace.setDefaultApplication(at:toOpen:)` 明確指定，
等同 Finder 的「取得資訊 → 打開方式 → 全部更改」，`make status` 可以查目前是誰。

一個會踩到的坑：預設程式是**用 bundle ID 存的**，不是路徑。
所以同一個 bundle ID 有兩份副本被 LaunchServices 註冊時（建置產物與安裝的那份），
解析結果不一定是你要的那份。因此 `.app` 一律組在 `.build/` 底下，
`~/Applications` 的那份才是唯一會被開到的；`set-default-app.swift` 也
優先挑 `~/Applications` 而不是用 bundle ID 反查。

開檔走 `NSApplicationDelegate.application(_:open:)`，一次開多個檔就開多個視窗，
政策見第 11 節。

## 9. 建置與安裝

```bash
make          # 取字型 → swift build -c release → 組 .app → codesign --sign -
make install  # 複製到 ~/Applications 並 lsregister
make run          # 建置後直接開
make set-default  # 把 .md 的預設開啟程式設成這個 App
make status       # 查 .md 目前的預設開啟程式是誰
make clean
```

`.app` 由 Makefile 手工組出來：

```
.build/MarkdownBrowser.app/Contents/
  Info.plist
  MacOS/MarkdownBrowser
  Resources/web/{index.html,app.js,base.css,themes/,vendor/}
  Resources/web/fonts/*.ttf
  Resources/{zh-Hant,en}.lproj/      宣告語言，標準選單才會跟系統變中文
```

ad-hoc 簽章（`codesign --sign -`），第一次開可能要去
「系統設定 → 隱私權與安全性」放行。

private GitHub repo。`.gitignore` 排掉 `.build/`、`.cache/`、`*.app`、`Resources/fonts/*.ttf`。
Commit 訊息用中文祈使句，比照 書庫 repo的習慣。

## 11. 視窗模型

多視窗。一個視窗讀一個檔，關掉最後一個視窗就結束 App。

### 11.1 狀態怎麼切

單視窗版本只有一個 `AppState.shared`，所以 Finder 再開一個檔就把正在讀的那一份
蓋掉。拆法是按「範圍」切，不是按功能切（見第 3 節的表）：

- 一個視窗一份的東西放 `DocumentState` —— 讀哪個檔、側欄、主題、字體、字級、外觀
- 跨視窗共用的放 `AppSettings` —— 新視窗的起始設定、最近開啟、自訂主題目錄
- 「誰開著、誰在前景」放 `WindowRouter`

**主題與字體是每個視窗各自的。** 並排比對兩套主題是這個 App 的實際用法，
而「記住上次選的」仍然成立 —— 任何視窗改了設定就寫回 `AppSettings`，
當下一個新視窗的起始值。

**前景視窗用 `NSWindow` 的 key 通知自己記一份，不用 SwiftUI 的 focus。**
選單要作用在前景視窗上，`⌘F` 的按鍵監聽也要找到前景視窗的 bridge，
而 AppDelegate 與 `NSEvent` 監聽都在 SwiftUI 的 focus 環境之外拿不到。
`WindowRouter.active` 是唯一的來源。它同時把前景視窗自己的變化轉發出去
（`objectWillChange`），否則開了檔之後選單的啟用狀態不會重算。

### 11.2 開檔的兩套政策

| 入口 | 政策 |
|---|---|
| Finder 雙點擊、`open` 指令、拖到 Dock | **不動已經開著檔的視窗** |
| `Cmd O`、最近開啟、側欄點擊 | 換掉前景視窗的內容；但那個檔**已經開在別的視窗**就改成把那個視窗帶到前景 |

Finder 那條依序試：已經有視窗在讀這個檔就帶到前景 → 還沒開檔的空白視窗載入它
→ 都沒有才開新視窗。第一條讓重複雙點擊不會開出兩個一樣的視窗，第二條讓
`Cmd N` 之後雙點擊不會多留一個空白視窗。

選單那條維持單視窗時的語意 —— 那是使用者當下指定的動作，要另開一個就先 `Cmd N`。

**一檔一窗。** 兩條政策都保證同一個檔只會開在一個視窗裡。原因是標記：每個視窗的
網頁端各自是標記資料的唯一真相（第 12.8 節），同一個檔開兩份就會兩邊各寫各的、
互相覆蓋。對閱讀器來說「同一章開兩個視窗對照」的需求很低，真要對照通常是兩個
不同章節。代價是 `Cmd O` 選了一個已經開在別處的檔，結果是跳到那個視窗、
目前的視窗不變。

Dock 圖示右鍵的選單要自己給（`applicationDockMenu`）—— 那個選單不會自動抄
App 的選單列，SwiftUI 的 `Commands` 只長在選單列上。目前只放「開新視窗」。

### 11.3 SwiftUI 的三個坑

都是實測踩到的，改動視窗相關的程式前先讀這一段。

**`WindowGroup` 不要帶值。** `WindowGroup(for: T.self)` 看起來剛好可以用「這個
視窗在讀哪個檔」當視窗的身分，但 SwiftUI 會把那個值存起來做視窗還原，而視窗內
換檔時要把新值寫回 binding，寫回去又會被當成「請開一個新視窗」—— 於是視窗數
每次啟動都往上加（實測乾淨啟動被還原成三個視窗，而且那份狀態清 UserDefaults
也清不掉）。現在 `WindowGroup` 不帶值，「新視窗要讀哪個檔」由
`WindowRouter.handoffs` 這個佇列交棒，新視窗的 `onAppear` 自己來取。

**開檔會冒出空殼視窗。** App 每次收到開檔請求，SwiftUI 都會生一個視窗又馬上
丟掉（帶著檔案啟動、以及執行中被 Finder 要求開檔都會）。被丟掉的那個只是內容
被拆走，視窗本體還留在畫面上，就疊在真正的視窗底下 —— `isVisible` 與
`orderedWindows` 都認為它在。把開檔處理全部停掉也一樣發生，所以這是 SwiftUI
自己的行為。`WindowRouter.closeOrphanWindows` 負責收掉：只關「本來有
`DocumentState`、現在沒有」的視窗，不掃全部視窗 —— 開檔對話框與關於視窗也
都沒有 `DocumentState`，掃全部會把它們一起關掉。

**而且那個空殼會半路把檔案接走。** 它在消失之前是個合法的「還沒開檔的空白
視窗」，所以可能被挑去載入檔案，也可能先取走交棒佇列裡的檔 —— 兩種都會讓
檔案跟著它一起消失，畫面上什麼都沒發生。實測空殼消失與開檔請求只差 2 ms，
而視窗大、內容多的時候順序就會反過來（真的開不出來）。順序賭不起，所以
`openFromFinder` 之後 0.4 秒回頭確認：沒有任何活著的視窗在讀那個檔就重開一次，
最多三次。

**一個視窗都還沒有的時候不要搶著開窗。** 帶著檔案啟動時，AppKit 會叫 SwiftUI
收掉它預設開的那個視窗（啟動是為了開文件，不是為了開空白視窗），而 Finder 的
開檔請求剛好落在那個空檔裡。這時自己開窗，就會跟 SwiftUI 接著補上的那個視窗
撞成兩個。所以沒有視窗時先把檔案存起來，等下一個視窗出現再接手。

還有一個時機問題：視窗掛上 SwiftUI 的過程中會呼叫 `WindowRouter.register`，
在那裡直接開檔會撞進 SwiftUI 的更新週期，所以待開的檔要晚一個 runloop 才處理。

## 12. 標記

在閱讀時畫重點、附註記。主要用途是**重讀時的視覺記號**；延伸用途是讓標記跟著
檔案走 —— 存成同資料夾的 sidecar 檔，跟著 `.md` 一起進 git。

**不做**：跨檔或跨書的標記總覽（那是書庫管理，第 2 節）、匯出、依顏色篩選、
搜尋標記、`Cmd Z` 復原、Markdown 格式的註記、模糊比對、列印標記。

設計過程用了兩個原型，實作完成、實機測過之後已經刪除（沒有保留分支）。它們驗證的結論都寫進了下面各節：

- `highlight-colors`：四種底色與底線在深色／淺色模式下疊上橘色粗體的實際對比，以及跟搜尋命中會不會撞色 —— 定案 12.1 節的配色與淺色模式的粗體壓深
- `highlight-interaction`：選取後浮出工具列、擦除選到的部分、純文字註記的自動儲存、tooltip 的延遲與位置、側欄「大綱｜標記」的分組與右鍵選單 —— 定案 12.2、12.3、12.6 節的操作方式

### 12.1 樣式

四種底色加一種底線：**綠、藍、紫、粉**、底線。預設是綠。

- **不用橘、不用黃。** 橘色是粗體字色，也是搜尋命中的底色；黃色離橘只差約 15°
  色相，疊在深色底上會變成橄欖褐，跟搜尋命中分不出來。
- **標記不改字重、不改字色。** 粗體＝橘色不加粗是這個 App 的核心訊號（第 1 節），
  標記只能動底色或底線，否則會跟粗體搶訊號。
- **淺色模式下標記內的粗體壓深一級**（`--hl-accent: #94481A`）。底色要淡到
  `#A2541A` 仍有 4.5:1，就只比紙色深一點點，畫了跟沒畫一樣；底色加深、
  粗體同步壓深，兩邊都看得清楚。仍然是橘色、仍然不加粗，不違反不變量。
- **深淺兩組都用半透明 `rgba`**，自訂主題換了底色時標記會自然融入。

| 變數 | 深色（疊在 `#1C1C1C`） | 淺色（疊在 `#FAF8F3`） | 粗體對比 深／淺 |
|---|---|---|---|
| `--hl-green` | `rgba(95, 184, 120, 0.24)` | `rgba(95, 184, 120, 0.30)` | 4.55 / 4.89 |
| `--hl-blue` | `rgba(95, 143, 208, 0.26)` | `rgba(95, 143, 208, 0.26)` | 4.78 / 4.77 |
| `--hl-purple` | `rgba(160, 124, 224, 0.28)` | `rgba(160, 124, 224, 0.26)` | 4.58 / 4.79 |
| `--hl-pink` | `rgba(224, 102, 143, 0.24)` | `rgba(224, 102, 143, 0.24)` | 4.97 / 4.81 |
| `--hl-underline` | `var(--fg)` | `var(--fg)` | — |
| `--hl-accent` | `var(--accent)` | `#94481A` | — |

變數依第 4 節的慣例：`base.css` 的 `:root` 放安全網（深色那組），兩個主題檔各自
提供深淺兩組。自訂主題沒提供時退回安全網 —— 半透明色在淺色底上只是比較淡，不會壞。

浮動工具列與 tooltip **不新增變數**，用主題既有的 `--bg`、`--fg`、`--rule`、
`--muted` 加陰影。工具列上的色票是按鈕圖示而不是內文樣式，用固定實色寫在 `base.css`。

### 12.2 建立、改色、擦除

**選取文字、放開滑鼠，選取範圍上方浮出工具列**（上方沒空間就放下方）：

```
● ● ● ● 底 │ 註記  拷貝  刪除
```

- 點顏色或「底」就建立標記。`Shift Cmd H` 直接套綠色。
- **刪除鍵永遠在**：選取範圍沒碰到任何標記時變灰（不隱藏，按鈕位置固定，手會記住）。
- **單擊已有的標記**也會浮出同一條工具列（編輯模式），目前的顏色有外框；
  這時的刪除是整條刪掉。**連結優先**：點到標記裡的連結文字是開連結，
  要編輯含連結的標記，點標記的其他地方或用選取範圍。
- 「拷貝」走 Swift 的 `NSPasteboard`，不用 `navigator.clipboard` —— 網頁是從
  自訂的 `mbres://` 載入的，WebKit 不一定當它是安全來源。

**建立時碰到既有標記：整條合併。** 新選取範圍與既有標記的聯集變成一條，用新顏色。

**刪除只擦掉選到的部分。** 選了某條標記中間的一段按刪除，就切成前後兩條；
選取範圍碰到幾條就各自擦掉重疊的部分。建立與擦除刻意不對稱：畫線時手不準，
所以碰到就合併；擦除時要精細，所以只擦選到的。

**選取範圍的整理規則**（建立或擦除之前先做）：

- 去掉頭尾的空白與換行 —— 從段落頭拖到段落尾常會多選到換行
- 限縮在內文區（拖進搜尋框的部分不算）
- 只剩空白就不算選取，不浮出工具列

**沒有禁區。** 標題、連結、行內程式碼、程式碼區塊、表格（跨儲存格就每格各畫一段）
都能標；圖片本身不畫，選取範圍跨過圖片時前後的文字照樣標。

### 12.3 註記

純文字、多行、一條標記一則。不渲染 Markdown。

- **新增**：工具列的「註記」，在工具列下方展開輸入框。在建立模式按「註記」會先用
  綠色（碰到既有標記就沿用它的顏色）建立標記，再開輸入框。
- **沒有存檔鍵、沒有取消**：停手 500 ms 就寫入，任何關掉輸入框的動作再寫一次 ——
  點別處、`Esc`、`Cmd Return`、點另一條或同一條標記、改色、再按一次「註記」、
  開始新的選取、視窗失去焦點、自動重載、關視窗。檔案隨時可能被 AI 改寫觸發重載，
  「關掉才存」會在最不該丟的時候丟。輸入框下方顯示「已自動儲存 時:分:秒」。
- **清空就是刪除註記**，標記本身留著。
- **標示**：有註記的標記，最後一段尾端加一顆同色系的上標小圓點。
- **閱讀**：點有註記的標記，工具列下方直接顯示全文，點文字就能編輯。
- **tooltip**：滑鼠停在有註記的標記上 **400 ms** 才出現（掃過去不會跳），放在整條標記
  **第一行的上方**（不蓋到標記本身；上方沒空間就放到最後一行的下方）。寬度上限約 22 字、
  最多 8 行，超過截斷。不可互動，移開就消失；工具列開著時不顯示。同一條標記跨行、
  跨段落的每一塊都算同一條，不重新計時。

**切割、擦光、合併時註記的去向**（原則：註記不會無聲消失）：

| 情況 | 處理 |
|---|---|
| 擦中間、切成兩段 | 註記**跟著前段** |
| 選取範圍會擦光整條有註記的標記 | 刪除鍵改成紅字「**刪除（含註記）**」，不跳對話框 |
| 建立時合併多條有註記的標記 | 註記依原文順序**串接**，中間空一行 |

### 12.4 sidecar 檔

```
書 F_心得_第1章_章名.md
書 F_心得_第1章_章名_highlights.json
```

檔名是 `<原檔名去掉副檔名>_highlights.json`，跟心得檔的底線命名風格一致。
側欄只列 Markdown 副檔名，所以 sidecar 不會跑進章節清單。**沒有標記就不建檔**，
全部刪光就刪檔。

```json
{
  "version": 1,
  "highlights": [
    {
      "id": "k3f9a2c1",
      "style": "purple",
      "exact": "致富的關鍵在於「知道自己要做什麼、和誰共事、什麼時候做」",
      "prefix": "一星期在餐廳工作 80 小時也不會變富有。",
      "suffix": "。努力不能少，但要用在對的地方；還沒弄清",
      "heading": "開場致富是一套學得會的技能",
      "note": "三個問題其實是同一個問題的三面：判斷力。",
      "created": "2026-10-13T14:16:57+08:00"
    }
  ]
}
```

| 欄位 | 說明 |
|---|---|
| `version` | 格式版本。比 App 支援的新就進入唯讀（12.9 節） |
| `id` | 8 碼隨機字串。不用陣列索引 —— 索引隨增刪位移，diff 會很亂 |
| `style` | `green` / `blue` / `purple` / `pink` / `underline`。叫 style 不叫 color，底線不是顏色 |
| `exact` / `prefix` / `suffix` | 引文錨點，**渲染後的文字**（不含 `**`），前後文各 32 字 |
| `heading` | 所在標題的 slug；標題之前的內容是 `null` |
| `note` | 純文字註記；沒有註記就**不寫這個鍵** |
| `created` | 建立時間，含時區，給總覽排序用 |

**刻意不存**：字元偏移量（上方插入一段就全部失效，得一直改寫 sidecar）、
`updated`（沒有功能用得到，又每改一次註記就變）、「找不到位置」的狀態（每次打開
算出來的，不是資料）、原檔名（檔名本身就是對應關係，再存一份改名後會互相矛盾）。

**寫檔原則：只有使用者的動作才會寫檔。** 打開、重新比對、發現某條對不上，都不寫。
否則唯讀閱讀器光是「打開來看」就會在 git 裡留下變動。寫入時：

- 縮排格式化、鍵的順序固定、標記依原文位置排序，`git diff` 只出現真正變動的行
- 原子寫入（寫暫存檔再 rename）
- **搭便車更新前後文**：成功對上的標記，順便把 `prefix` / `suffix` / `heading` 更新成
  現況；找不到位置的標記原封不動保留，依它上次在檔案裡的位置排

**git**：`~/books` 是 private repo，sidecar 照常追蹤，因此有版本歷史與備份。
但**不跟心得檔混在同一個 commit**，規則寫在那個 repo 的 `CLAUDE.md`。
**repo 若改成公開，註記會跟著公開，而且留在 git 歷史裡很難清乾淨。**

**純文字檔一視同仁**，App 打得開的檔都能標。`X.md` 與 `X.txt` 同時存在時會共用
`X_highlights.json`；後果只是各自把對方的標記列成「找不到位置」，不會遺失資料。

### 12.5 錨點與重新比對

錨點是引文比對（W3C Web Annotation 的 TextQuoteSelector 做法），不是位置。
位置型錨點（像 EPUB 的 CFI）能用是因為電子書出版後不會變；心得檔會被 AI 改寫，
上方插入一段，位置型錨點就全部錯位 —— 落在錯的句子上比消失還糟。

**比對規則**（先把空白連續段壓成一個，AI 重排換行不受影響）：

1. 找出 `exact` 所有出現的位置
2. **只出現一次就直接接上**，就算前後文已經被改掉。句子本身還在，就是同一句
3. 出現多次：前文從尾端往前連續相同的字數 ＋ 後文從開頭往後連續相同的字數，
   `heading` 相同再加分；取最高分，同分取第一個
4. 一次都沒出現：列入「找不到位置」

比對的是渲染後的文字，所以 AI 在句子裡加上或拿掉 `**`，標記照樣對得上。

**時機**：就在 `MB.render` 裡、畫面更新前同步做完，標記與新內容同一個畫面出現。
一章幾千到一萬字、幾十條標記，是毫秒以下的工作，不需要 Worker 或增量比對。

**重載當下正在操作的東西**：

| 狀態 | 處理 |
|---|---|
| 正在打註記 | 先寫入；重新比對後那條還在就保持輸入框開著並重新定位，不在就關掉 |
| 工具列在建立模式 | 關掉（選取範圍的位置已經失效） |
| 工具列在編輯模式 | 那條還在就重新定位，不在就關掉 |
| tooltip | 關掉 |

AI 連續改檔的中間版本可能讓某條暫時對不上；因為重載不寫檔，下個版本對上就回來。

### 12.6 側欄的標記總覽

側欄上半「同資料夾」不動，下半用分段控制切換「**大綱 | 標記 n**」，每個視窗各自記住。
只列**目前這個檔**的標記。

```
[ 大綱 | 標記 5 ]
開場：致富是一套學得會…        ← 所在標題（灰色小字），依原文順序分組
● 一星期在餐廳工作 80 小時…    ← 原文最多 2 行
  跟「窮忙」是同一件事…        ← 註記第 1 行，灰色斜體
▁ 把自己商品化                 ← 底線樣式用短橫線
⚠ 找不到位置（1）              ← 永遠排最後
```

- **點一列**：內文捲到那條標記、閃兩下，**不開**工具列（只是導航）
- **右鍵**：拷貝原文、拷貝註記（沒註記就變灰）、刪除（有註記就是紅字「刪除（含註記）」）
- **找不到位置**：點了不捲動，原地展開完整原文與註記，讓你判斷要不要刪
- 「標記」後面的數字含找不到位置的那些

### 12.7 選單

依作用對象分散到現有選單，不新增「標記」選單（比照預覽程式的「標示文字」在工具選單）：

| 選單 | 項目 | 備註 |
|---|---|---|
| 編輯 | 標記選取文字 `Shift Cmd H` | 永遠可按，沒有選取時只發出提示音 |
| 檔案 | 在 Finder 中顯示標記檔 | 還沒有 sidecar 時變灰 |
| 顯示方式 | 側欄：大綱／側欄：標記 | 單選，不加快捷鍵 |

`Shift Cmd H` 跟 `Cmd F` 一樣走 `NSEvent` local monitor、比對 `keyCode`（4 = H），
選單上只是顯示快捷鍵。

### 12.8 架構

**網頁端是標記資料的唯一真相，Swift 只負責讀寫檔與鏡像給側欄。** 合併、擦除、
錨點比對都需要渲染後的文字位置，只有網頁端拿得到；讓 Swift 持有模型的話，
這些邏輯最後還是得問網頁端，會分散在兩邊。

| 方向 | 介面 | 用途 |
|---|---|---|
| Swift → JS | `MB.render(markdown, {keepScroll, highlights})` | 換檔時同一次呼叫送進 sidecar 內容（含唯讀狀態），標記與內文同一個畫面出現；重載同一份文件不帶 `highlights`，沿用記憶體裡的 |
| Swift → JS | `MB.setHighlights(payload)` | sidecar 被外部改動、或認領孤兒之後重新載入 |
| Swift → JS | `MB.setHighlightBanner(text, actions)` | 警示列（12.9 節）；`null` 收起 |
| Swift → JS | `MB.revealHighlight(id)` | 側欄點一列 |
| Swift → JS | `MB.deleteHighlight(id)` | 側欄右鍵刪除 |
| Swift → JS | `MB.highlightSelection()` | `Shift Cmd H`；回傳有沒有建立，沒有就發提示音 |
| Swift → JS | `MB.commitNote()` | 視窗失去焦點、換檔、改名、關窗、結束前先把註記寫入；回傳寫入的內容，網頁端來不及送訊息時 Swift 自己寫 |
| Swift → JS | `MB.probeHighlights(candidates)` | 認領孤兒 sidecar 前試比對；回傳每份對得上幾條／總共幾條 |
| JS → Swift | `highlights` | 比對後的清單，側欄鏡像 |
| JS → Swift | `saveHighlights` | `{doc, json}`：完整 sidecar 內容或 `null`（刪檔）。帶著 `doc` 是因為換檔前最後一筆註記會晚一步到，要寫回它自己的 sidecar |
| JS → Swift | `copy` | 拷貝文字，走 `NSPasteboard` |
| JS → Swift | `bannerAction` | 警示列上的按鈕：重試、在 Finder 中顯示 |

需要回傳值的三個（`highlightSelection`、`commitNote`、`probeHighlights`）直接用
`evaluateJavaScript` 的完成回呼拿，不另外設計訊息。

**sidecar 也要監聽**：`git pull`、`git checkout` 會從外部改它。不另外掛一個檔案監聽
（sidecar 常常還不存在，`FileWatcher` 開不了檔就會一直重試），而是搭現有的資料夾
監聽 —— git 與 App 自己都是「寫暫存檔再 rename」，一定會反映在資料夾上。
App 自己寫檔也會觸發事件，所以收到事件先比對內容，跟最後一次讀到或寫入的一樣就忽略；
讀不出來的壞檔也記下原文，同一份壞檔不會反覆觸發。

### 12.9 寫不進去或讀不出來

| 情況 | 處理 |
|---|---|
| 資料夾不能寫（DMG、唯讀磁碟） | 開檔時檢查。工具列照樣浮出、拷貝能用，其他按鈕變灰，底下寫「此資料夾無法寫入，不能標記」；已有的 sidecar 照樣顯示 |
| 寫入失敗（磁碟滿、被鎖住） | 不跳對話框（註記每 500 ms 寫一次會連續轟炸）。內文頂端出現不擋操作的警示列與「重試」，標記留在記憶體、下次異動自動重試。**關視窗、換檔、結束 App 時還有沒寫進去的**才跳對話框：再試一次／拷貝為 JSON／放棄。這三個時機都要先等網頁端把最後一筆註記寫完（`commitNote` 的回呼）再判斷，否則最後一筆寫入失敗時對話框已經錯過 |
| sidecar 解析失敗、`version` 太新、或有看不懂的條目 | **一律唯讀，絕不覆蓋**。看不懂的條目（樣式不認得、欄位型別不對）網頁端載入時會略過，下一次存檔就等於刪掉它們，所以只要有一條就整個檔唯讀。git 合併衝突留下的 `<<<<<<<` 就是這種情況 —— 當作「沒有標記」的話，畫一條線就會把衝突檔連同兩邊的標記一起蓋掉。警示列寫明原因並附「在 Finder 中顯示」，修好後監聽偵測到改動就自動解除 |

不做備援位置（例如改存到 `~/Library/Application Support/`）：多一個存放地點就要處理兩邊合併。

### 12.10 改名

改名幾乎都是 AI 做的，三層處理：

1. **源頭**：`~/books/CLAUDE.md` 規定改 `.md` 檔名時，同名的
   `_highlights.json` 一起 `git mv`。
2. **App 開著時**：`FileWatcher` 收到 `.rename`，在重掛監聽之前用
   `fcntl(fd, F_GETPATH)` 問出還開著的 fd 現在的路徑。舊路徑沒有馬上又出現
   （排除編輯器「寫暫存檔再 rename 蓋過去」的原子存檔）、而且新路徑不在垃圾桶裡
   （丟進垃圾桶在檔案系統上也是一次 rename，跟過去的話 sidecar 會被搬進垃圾桶），就是真的改名：
   視窗跟到新檔，sidecar 一起改名。這是「只有使用者動作才寫檔」唯一的例外 ——
   它是在跟上一個已經發生的改名，比留下孤兒乾淨。順便修掉「改名後視窗卡在舊內容、
   每 0.3 秒重試開舊路徑」的舊 bug。
3. **App 沒開著時**：打開一個沒有 sidecar 的檔，掃**同資料夾**裡「對應的檔已經不存在」
   的 sidecar，拿它的 `exact` 試比對目前內容。**過半數**對得上就詢問
   「找到 12 條可能屬於這個檔案的標記（來自 `舊檔名`），要接上嗎？」，同意才改名接上。

### 12.11 列印

**不印標記也不印註記。** 列印與 PDF 輸出跟沒有標記時完全一樣：`print.css` 拿掉
`mark.mb-hl` 的底色、底線與註記圓點，工具列、tooltip、警示列一律隱藏。
